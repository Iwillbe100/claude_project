어떤 문제인가

구현·시뮬레이션 문제는 어려운 알고리즘 없이, 길게 주어진 규칙을 빠짐없이 그대로 코드로 옮기는 것이 핵심이다. 로봇이 움직이고, 프린터가 작업을 처리하고, 명령에 따라 표가 바뀌는 식이다. B형은 이런 규칙이 여러 함수에 걸쳐 있어서, 한 군데만 잘못 구현해도 케이스 전체가 0점이 된다.

시간 제한보다 정확성이 먼저 문제가 된다. 알고리즘을 아는 것보다 규칙을 정확히 읽고 정리하는 습관이 중요하다.

풀이 순서

  1. 규칙을 번호를 붙여 적는다. 문제 문장을 "조건 → 결과" 한 줄씩으로 쪼갠다. (예: "다음 칸이 벽이면 멈춘다", "같은 시각이면 번호가 작은 프린터가 먼저")
  2. 상태를 정한다. 시간이 지나도 기억해야 하는 값이 무엇인지 적는다. (로봇 위치와 방향, 어느 칸이 찼는지, 대기열)
  3. 함수마다 처리 순서를 적는다. 검사 → 상태 변경 → 반환값 순서로 쓴다.
  4. 예시를 손으로 따라간다. 상태가 어떻게 변하는지 표로 그려 보면 규칙의 빈틈이 보인다.
  5. 그다음에 코드를 쓴다.

도구 1: 방향 배열과 회전

방향을 번호로 두고 이동량을 배열로 만들면 if 네 줄이 한 줄로 줄어든다. 방향 번호는 시계 방향 순서로 매기면 회전이 덧셈이 된다.

DR = (-1, 0, 1, 0)      # 0:위  1:오른쪽  2:아래  3:왼쪽
DC = (0, 1, 0, -1)

d = (d + 1) % 4          # 시계 방향 90도
d = (d - 1) % 4          # 반시계 90도 (파이썬은 음수 % 도 0~3이 나온다)
d = (d + k) % 4          # k가 -100이든 100이든 한 줄

nr, nc = r + DR[d], c + DC[d]
C++에서는 -1 % 4가 -1이 나와서 (d + k + 4) % 4처럼 써야 하지만, 파이썬은 그럴 필요가 없다.

도구 2: 이동은 한 칸씩, 검사는 순서대로

"가다가 막히면 멈춘다"는 규칙은 한 칸씩 가면서 다음 칸을 먼저 검사하는 반복문으로 쓴다. 검사 순서가 중요하다. 범위를 먼저 확인해야 범위 밖 인덱스를 읽지 않는다.

def move(robot_id, steps):
    r, c, d = robots[robot_id]
    moved = 0
    for _ in range(steps):
        nr, nc = r + DR[d], c + DC[d]
        if not (0 <= nr < n and 0 <= nc < n):    # 1. 격자 밖
            break
        if wall[nr][nc] == 1 or occ[nr][nc] != 0:   # 2. 벽, 다른 로봇
            break
        occ[r][c] = 0                              # 이전 칸 비우기
        occ[nr][nc] = robot_id                     # 새 칸 채우기
        r, c = nr, nc
        moved += 1
    robots[robot_id][0], robots[robot_id][1] = r, c   # 로봇 정보도 갱신
    return moved                                      # '실제로 움직인 칸 수'

도구 3: 같은 정보를 두 군데 저장하면 동기화가 숙제

로봇 목록(robots)과 칸 점유(occ)처럼 같은 사실을 두 가지 방식으로 저장하면 조회는 빨라지지만, 바꿀 때 두 곳을 항상 같이 바꿔야 한다. 로봇을 치울 때 occ를 비우지 않는 것이 가장 흔한 버그다.

상태를 바꾸는 코드를 함수 몇 개로 모아 두고, 다른 곳에서는 그 함수만 쓰면 실수가 줄어든다.

도구 4: 시간이 흐르는 시뮬레이션

시간이 최대 100만까지 가는 문제에서 시간을 1초씩 흘려보내면 느리다. 실제로 무언가 일어나는 순간만 처리하는 이벤트 기반 방식을 쓴다.

틱(1초씩) 방식이벤트 방식
구현단순하고 틀리기 어렵다힙이 필요하다
속도O(시간 길이)O(사건 수 × log)
언제시간 범위가 작을 때, 검증용시간 범위가 클 때

busy = []        # (끝나는 시각, 프린터 번호)

도구 5: 동시에 일어나는 일의 순서

"같은 시각에 끝나면 번호가 작은 프린터 먼저"처럼 동점 규칙이 문제에 숨어 있다. 힙에 튜플로 넣으면 앞 칸이 같을 때 다음 칸으로 비교하므로, (끝나는 시각, 프린터 번호) 한 줄로 규칙이 해결된다.

또 "시각 T에 호출되면 T 이하에 끝나는 일은 이미 끝난 것"처럼 경계 시각을 포함하는지가 문제마다 정해져 있다. <와 <= 하나가 답을 바꾼다. 문제 예시에서 경계 사례를 찾아 확인하자.

틀렸을 때 디버깅하는 법

  • 직접 입력 실행으로 아주 작은 입력(로봇 1대, 3 × 3 격자)을 만들어서 규칙 하나씩 확인한다.
  • 느리지만 확실한 방식(틱 방식, 리스트 전체 훑기)으로 한 번 더 짜서 결과를 비교한다. 시험장에서는 시간이 없으니 연습 때 해 두자.
  • 항상 참이어야 하는 조건을 assert로 걸어 둔다. (예: occ에 적힌 로봇의 위치가 robots와 같은가)
  • 첫 번째로 틀리는 호출을 찾는다. 어느 줄에서 처음 어긋나는지 알면 원인이 거의 정해진다.

자주 하는 실수

  • 검사 순서. 범위 확인 전에 wall[nr][nc]를 읽으면 -1 인덱스가 반대편 칸을 읽어서 조용히 틀린다.
  • 반환값의 의미. move가 돌려주는 것은 "요청한 칸 수"가 아니라 "실제로 움직인 칸 수"다.
  • 삭제 후 정리. 치운 로봇이 차지하던 칸을 비우지 않는다.
  • 경계 시각. 끝나는 시각과 호출 시각이 같을 때 어느 쪽이 먼저인지 놓친다.
  • init 초기화. 이전 테스트 케이스의 로봇·대기열이 남는다.
