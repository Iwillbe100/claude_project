## 읽기 0 — 진입 조건 (후보가 없으면 STEP 6 은 하지 않는다)

**STEP 6 은 모두가 하는 단계가 아닙니다.** 킷에는 처방 가지 3개(`encoding` · `image_dead` · `image_spec`)가
이미 들어 있고 그래프 안에서 늘 돕니다 — 진단은 매번 켜지고, 가지는 그 실패가 났을 때만 켜집니다.
실행에서 그 실패가 안 나면 진단만 지나갑니다. **새 실패가 로그에 되풀이해서 남을 때만** 이 STEP 에서
같은 방식으로 가지를 하나 더합니다.

먼저 실패 기록 보고서를 봅니다.

```bash
python scripts/failure_report.py            # 가장 최근 실행 하나
python scripts/failure_report.py --all      # 이 킷의 실행 전부
python scripts/failure_report.py <폴더>…     # 모은 기록 (강사가 여러 교육생 것을 모아서)
```

보는 칸은 둘입니다.

```text
③    아직 처방 가지가 없는 실패          규칙표에 없는 부족 · 수집 실패 · 처방 가지 <이름> 가 못 맡음 ·
                                         처방 가지 <이름> 가 못 고침
                                         [일화]                          한 번
                                         [후보]                          같은 줄 2번 이상 · 또는 2실행 이상
                                         [패턴 — 킷 처방 가지 후보]      서로 다른 실행 3곳 이상
③-2  재수집(LLM)이 반복해서 맡은 원인    가지 없이 SHORT 로 남아 재수집(루프 A) · 재생성 · rebuilder(루프 B)로 간 원인
                                         [후보]                          한 실행에서 2바퀴 이상 · 또는 2실행 이상
                                         [패턴 — 킷 처방 가지 후보]      3실행 이상
                                         [한 번 — 재수집이 맡으면 된다]  그 밖
```

**③-2 가 따로 있는 이유.** 원인 규칙표 끝의 포괄 규칙(`목표` → "개수가 모자람")에 걸린 부족은 '그 밖'이
아니라서 ③ 에 뜨지 않습니다. 그런데 그 부족이 재수집(LLM)을 몇 바퀴 돌아도 남는다면 — 토큰을 쓰고 매번
다른 결과를 내며 같은 실패를 되풀이한다면 — 그것이 바로 규칙으로 뺄 후보입니다. 보고서는 진단 기록의
`causes` · `loop_iter` 로 (루프, 원인)마다 **서로 다른 바퀴 수**를 셉니다. '그 밖' 원인은 ③ 이 줄마다
보여 주므로 ③-2 에서는 뺍니다. **재현(inject) 실행은 ③ · ③-2 둘 다에서 세지 않습니다** — 일부러 다시 일으킨
실패는 로그에 "남은" 실패가 아니고, STEP 6 의 빨간불 확인 실행이 제 가지를 후보로 올리는 일도 막습니다.
**replay 실행은 ③-2 에서 세지 않습니다** — replay 의 재수집은 LLM 이 아니라
인계본을 잘라 쓰므로 "1바퀴 부족 → 2바퀴 PASS" 가 늘 같고, 여러 번 돌리면 가짜 패턴이 됩니다.

보고서의 끝 줄이 들어갈지를 알려 줍니다.

```text
후보가 있을 때
 다음: 후보 하나를 골라 specs/06_DETOUR.md 의 `읽기 5` 에 적고 `STEP 6 진행해줘`
       (같은 입력에 같은 고칠 법이 없으면 재수집에 그대로 둡니다 — 06_DETOUR `읽기 4`)

후보가 없을 때 — ③ · ③-2 가 비었다
 이번 실행의 실패는 이미 처방 가지와 재수집이 맡았습니다 — STEP 6 은 하지 않아도 됩니다
 (live · --all · 여러 교육생의 기록을 모은 폴더에서 후보가 생기면 그때 합니다)

후보가 없을 때 — ③ 에 한 번 나온 [일화] 뿐이다
 한 번 나온 실패(일화)뿐입니다 — STEP 6 은 하지 않아도 됩니다
 (같은 실패가 되풀이되면 — 다음 실행 · --all · 모은 폴더에서 [후보]가 되면 — 그때 합니다)
```

**후보가 없으면 "STEP 6 불필요" 로 끝냅니다.** 이것도 정상적인 끝입니다. 이 문서는 `DRAFT` 로 두고
(`validate_specs.py --step 6` 의 SHORT · exit 2 는 오류가 아닙니다) 결과 정리(`evidence-review`)로 갑니다.
**replay 기본 실행은 ③ · ③-2 가 모두 비는 것이 정상입니다** — 인계본이 멀쩡하고, replay 재수집은 세지
않기 때문입니다. 후보는 live 실행 · `--all` · 모은 폴더에서 나옵니다.

**후보가 있으면 두 가지를 묻고 들어갑니다** (읽기 1 의 절차 ③ · ④).

```text
되풀이됐나?                        ③ · ③-2 의 [후보] · [패턴 …] (③ 은 같은 줄 2번 이상)
                                   아니오 ([일화] 한 줄 · [한 번 …] 뿐) → 아직 일화. 로그가 더 쌓이면 다시 본다
같은 입력에 같은 고칠 법이 있나?   예     → 처방 가지 (이 STEP)
                                   아니오 → 재수집(LLM)에 그대로 둔다 — 읽기 4 의 가려내기
```

## 읽기 1 — 이 STEP에서 정하는 것

**루프에 없던 것입니다 — 되풀이된 실패가 가지가 됩니다.**

```text
루프          실패하면 "한 바퀴 더". 원인이 무엇이든 같은 바퀴를 다시 돈다
그래프        원인마다 다른 길. "정해진 고칠 법이 있는 실패"는 규칙 처방 가지로 빼서
              규칙대로 고치고 → 같은 시험지로 재검하고 → 루프 골격의 검사기로 돌아온다
              남은 것만 재수집(LLM)이 맡는다
```

두 길은 이렇게 다릅니다.

```text
                재수집(LLM)  repair_*        처방 가지  fix_<이름> → test_<이름>
무엇을 받나     원인을 몰라도 받는다         알아본 원인만
같은 입력이면   매번 다른 결과               같은 결과
비용            토큰 · 바퀴를 쓴다           LLM 호출 0 · 바퀴를 쓰지 않는다
안 되면         바퀴 상한 3 → ★게이트        처방 한도 2 → ★게이트
```

`image_dead` 의 live 2회째 Commons 검색도 LLM 을 부르지 않습니다. 루프 B 에서 재수집에 해당하는 LLM 쪽은
**게이트 B → `rebuilder`** 입니다 — 루프 B 의 자동 `retry` 는 결정론 렌더러를 다시 돌릴 뿐입니다.

그래프로 옮긴 이득이 여기서 셋으로 보입니다.

```text
추적   원인마다 다른 길이 그림에 그대로 남는다    Studio 에서 처방 가지에 불이 들어온다
확장   같은 모양으로 늘린다                       등록부 한 줄 = 노드 두 개 + 간선 셋
재현   그 실패를 다시 일으켜 같은 길을 태운다     --inject <이름> · Studio 입력 {"inject": [...]}
```

**재현(inject)** 은 이미 있는 가지가 켜지는 것을 보거나, 새 가지의 시험지 빨간불을 먼저 볼 때 그 실패를
다시 일으키는 장치입니다. 무엇을 가지로 만들지는 재현이 아니라 **로그**가 정합니다 (읽기 0).

**그래프가 자라는 방향.** 처음에는 원인을 몰라도 모든 부족이 재수집(LLM)으로 갑니다. 같은 실패가 로그에서
되풀이되고 고칠 법이 정해지면, 그 실패만 가지로 빼서 LLM 보다 먼저 규칙으로 받습니다. 킷의 가지 3개가
그렇게 자란 결과이고(읽기 3 (13)), 이 STEP 은 같은 방식으로 **내 로그의** 실패 하나를 더합니다.

**노드를 늘리는 것은 문제가 난 지점에서만 허용합니다.** 루프 골격(노드 14개)은 잠겨 있고,
처방 가지는 검사기 바로 뒤의 **진단 노드**에서만 갈라집니다. 그래서 이 STEP 은 결정을 묻지
않습니다 — 모양은 킷이 정해 두었고, 교육생이 채우는 것은 **내 실패에 대한 답**입니다 (읽기 4).

```text
관찰 (5분)

 ③ 묻는다   되풀이됐나?                          아니오 → 끝 ("STEP 6 불필요" — 읽기 0)
 ④ 가른다   같은 입력에 같은 고칠 법이 있나?     아니오 → 재수집(LLM)에 그대로 둔다 (읽기 4)
가지 (15분)
 ⑤ 만든다   new_detour.py <이름> --loop A|B --title "…"   세 조각 · 구조 검사 12행 PASS (아직 그대로 돈다)
 ⑥ 빨간불   시험지 + inject() 먼저 → --inject <이름> 으로 그 실패를 재현 → test_<이름>: FAIL · 게이트 정지
 ⑦ 초록불   fix() → 같은 명령 → test_<이름>: PASS … (검사기로 복귀)

```

### 관찰 (5분) — ① 돌린다 · ② 본다

**내 실행을 봅니다.** 읽기 0 의 보고서에서 후보 줄을 고르고, 같은 실행의 `history` 에서 그 실패가 어디서
났는지 봅니다 — `run_once.py` 끝의 `history — 검사기 · 진단 · 처방 가지 · 게이트 줄만`, 또는 Studio 결과 패널의
`history`. 진단 줄이 무엇을 골랐는지가 핵심입니다.

```text
diagnose_info: 처방 가지 대상 없음 → 루프 골격 그대로                  평소 — 진단은 매번 켜진다
diagnose_info: ▷ <title> — 증상 N곳 → 처방 가지 fix_<이름> (1/2회째)   진단이 가지를 골랐다
diagnose_page: 증상은 있지만 처방 가지를 타지 않음 (<이름>: <why> · …) → 루프 골격 그대로
```

`처방 가지 대상 없음` 뒤에 SHORT 가 이어져 재수집(`repair_*`)으로 간 바퀴가 여럿이면 그 부족이 ③-2 로
올라옵니다. Studio(`langgraph dev`)로 돌렸다면 LangSmith 에서 그 바퀴의 `repair_*` 아래
`claude -p · repair_city[<도시>]` run 을 열어 모델이 무엇을 되풀이했는지 봅니다. 터미널 `run_once.py` 는
`.env` 를 읽지 않으므로 트레이스가 남지 않습니다.

**가지 하나가 켜진 모양 — 킷의 `image_dead` 를 재현해 봅니다.** 내 가지를 다 만들면 이렇게 돕니다.

```bash
python scripts/run_once.py --mode replay --inject image_dead --auto stop
python scripts/failure_report.py
```

킷의 처방 가지 `image_dead` 가 맡는 실패(모델이 해시를 지어낸 사진 주소)를 재현하고 돌린 것입니다. `--auto stop` 은
게이트 A 에서 끝내라는 뜻입니다 — `run_once.py` 는 `--auto` 의 답을 다 쓰면(또는 표준입력이 터미널이 아니면)
권장값으로 넘어가지 않고 그 게이트에서 끝냅니다. 터미널에는 노드가 켜진 순서가 찍힙니다.

```text
 [   0.0s]  7  check_information
              info_verdict = SHORT
 [   0.1s]  8  diagnose_info
              failure_kind = image_dead          ← 진단이 원인을 골랐다
 [   0.1s]  9  fix_image_dead
              cities += 3
 [   0.1s] 10  test_image_dead
              detour_verdict = PASS
 [   0.1s] 11  check_information                 ← 루프 골격의 검사기로 복귀
 [   0.1s] 12  diagnose_info
              failure_kind =                     ← 더 고칠 것 없음 → 루프 골격 그대로
 [   0.1s] 13  repair_city
 ...
 처방 가지   : fix_image_dead   (실패 기록: evidence/failures/run-YYYYmmdd-HHMMSS.jsonl)
 ...
 history — 검사기 · 진단 · 처방 가지 · 게이트 줄만     ← 끝에 아래 history 의 그 줄들이 그대로 찍힌다
```

`--thread` 를 주지 않으면 실행마다 새 이름(`run-날짜-시각`)이 붙고 실패 기록도 실행마다 따로 생깁니다.

Studio 에서는 입력 칸에 `{"inject": ["image_dead"]}` 를 넣으면 같은 길이 켜지고, 결과 패널의
`history` 에 이렇게 남습니다 (터미널 끝의 history 는 이 중 검사기 · 진단 · 처방 가지 · 게이트 줄만 보여 줍니다).

```text
read_request: 베트남 · 실행 모드 replay
  ↳ ⚠ 실패 재현(inject) 예약: image_dead — 수집 직후 그 실패를 다시 일으키고, 진단 노드가 찾아 처방 가지로 보냅니다
...
collect_city[하노이]: replay 로 수집
  ↳ ⚠ 실패 재현 [image_dead] 하노이/탕롱 황성 사진 주소를 해시 두 글자(8/8c)를 지어낸 upload 주소로 (404 — 실측 모양)
...
check_information: SHORT · 부족 12곳 · 1바퀴
diagnose_info: ▷ 이미지 주소가 죽어 있음 — 증상 1곳 → 처방 가지 fix_image_dead (1/2회째)
fix_image_dead: 1/2회째 · 고침 1곳 · 못 고침 0곳
  ↳ 하노이/탕롱 황성 이미지: 해시가 든 주소를 권장 형태로 바로잡았습니다 (Special:FilePath/Central_Sector_of_the_Imperial_Citadel_o)
test_image_dead: PASS · 1/2회 → check_information (검사기로 복귀)
check_information: SHORT · 부족 9곳 · 1바퀴 (처방 가지에서 복귀 — 바퀴를 쓰지 않음)
diagnose_info: 처방 가지 대상 없음 → 루프 골격 그대로
repair_city[하노이]: replay 로 3곳 보정          ← 그다음은 루프 골격이 하던 일 그대로
...
check_information: PASS · 부족 0곳 · 2바퀴
diagnose_info: 처방 가지 대상 없음 → 루프 골격 그대로
human_gate_a: stop
```

부족이 12곳 → 9곳으로 줄었는데 바퀴는 **1바퀴 그대로**입니다 — 처방 가지는 바퀴를 쓰지 않습니다.

이 실행의 `failure_report.py` 는 ② 에 `image_dead       들어감 1번 · 시도 1번 · 합격 1번`
(들어감 = 진단이 보낸 횟수 · 시도 = fix → test 를 돈 횟수)을 보여 주고, ③ · ③-2 는 비어 있으며 끝 줄은
`STEP 6 은 하지 않아도 됩니다` 입니다 — **재현한 실패는 후보가 아닙니다** (이미 킷의 가지가 맡았고, 보고서는 재현(inject)
실행을 ③ · ③-2 에서 세지 않습니다 — `(재현(inject) 실행 1개는 ③ · ③-2 에서 세지 않았습니다 …)`).
③ 에 올라오는 것은 네 종류입니다 — `규칙표에 없는 부족` · `수집 실패` · `처방 가지 <이름> 가 못 맡음`(증상은
있는데 진단이 보내지 않음 — 처방 한도를 이미 다 썼거나 · 정성 회차 중이거나 · 시험지가 멈춤) ·
`처방 가지 <이름> 가 못 고침`(탔지만 처방 한도를 다 쓰고 게이트로 감).

**`replay` 에서 재현하지 않으면 처방 가지는 한 번도 켜지지 않습니다** (`live` 에서는 그 실패가 실제로 나면
켜집니다 — 그것이 가지의 본래 일입니다). 진단 노드는 매번 켜지지만
`처방 가지 대상 없음 → 루프 골격 그대로` 를 적고 지나갑니다.

### ③ 묻는다 · ④ 가른다

후보가 **되풀이됐는지**(읽기 0), **같은 입력에 같은 고칠 법이 있는지**(읽기 4 의 가려내기) 묻습니다.
둘 다 "예"인 것만 ⑤ 로 갑니다. 아니면 이 STEP 은 거기서 끝입니다 — 그 실패는 재수집(LLM) · 게이트가 계속
맡고, 로그가 더 쌓이면 다시 봅니다.

## 읽기 3 — 이미 정해 둔 것 (읽고 넘어가기)

### (1) 그래프는 세 겹입니다 (고정)

```text
          ┌── 루프 A 모은다 ──┐         ┌── 루프 B 만든다 ──┐         ┌─ 루프 C 다듬는다 ─┐
 START → 수집 → 검사 → ◇진단 A → ★게이트 A → 페이지 → 검사 → ◇진단 B → ★게이트 B → 정성 3회 → END
                  ▲       │                         ▲       │
                  └─▷가지──┘                         └─▷가지──┘
               (encoding · image_dead)              (image_spec)
                고치고 → 시험 → 복귀                  고치고 → 시험 → 복귀
```

▷ 가지 = 규칙 처방 가지. 새 가지는 같은 자리(진단 A · 진단 B)에 붙습니다 — 로그에 후보가 있을 때 (STEP 6).

| 겹 | 노드 | 늘어나나 |
| --- | --- | --- |
| 루프 골격 | 14개 — STEP 1~5 에서 다룬 그대로 | **늘지도 줄지도 않는다** |
| 진단 | 2개 — `diagnose_info`(검사기 A 뒤) · `diagnose_page`(검사기 B 뒤) | 그대로 |
| 처방 가지 | 등록부 한 줄마다 2개 — 킷 기본 3개 × 2 = 6 | **여기서만 늘어난다** (후보가 있을 때) |

킷을 받은 그대로는 **노드 22개**(14 + 2 + 3×2)입니다. 처방 가지를 하나 더하면 24개가 됩니다.

### (2) ★ 처방 가지 하나의 모양 — 모두 같습니다 (고정)

```text
 check_* ─▶ ◇diagnose_* ─┬─ (처방 가지 대상 없음) ────────────▶ 루프 골격 그대로
                         └─ <이름> ─▶ fix_<이름> ─▶ test_<이름> ─┬ 합격           → check_*   (검사기로 복귀 · 바퀴 안 씀)
                                                                ├ 불합격 · 한도 안 → fix_<이름> (한 번 더)
                                                                └ 불합격 · 한도 끝 → ★human_gate_* (사람)
```

| | 루프 A 처방 가지 | 루프 B 처방 가지 |
| --- | --- | --- |
| 갈라지는 곳 | `diagnose_info` | `diagnose_page` |
| 합격하면 (`back`) | `check_information` | `check_page` |
| 처방 한도를 다 쓰면 (`gate`) | `human_gate_a` | `human_gate_b` |
| 시험지가 읽는 것 | `output/research_data.json` | `output/travel_site.html` |

`build.py` 가 등록부를 읽어 **반복문으로** 붙입니다. `fix → test` 는 정적 간선 하나,
`test` 뒤는 `route_after_detour` 가 고르는 세 길(`back` · `retry` · `gate`)뿐입니다.
배선을 손으로 짜지 않으므로 틀릴 곳이 없습니다.

`check_graph_shape.py` **11번(처방 가지 계약)** 이 이 모양을 확인합니다. 11번이 걸리면 이 그림과
`python scripts/new_detour.py` 가 만드는 모양을 비교하십시오.

```text
11번이 보는 것
 (a) 루프 골격 14 · 진단 2 · 등록된 처방 가지 밖의 노드가 없다
 (b) 검사기 → 진단은 정적 간선 하나뿐
 (c) 모듈 · 시험지가 제자리에 있고, 모듈이 fix(data, *, attempt, mode) · inject(obj) · INJECT_AT 모양이다
 (d) 처방 가지는 진단에서만 갈라진다
 (e) fix → test 정적 하나 · test 뒤 {back: 그 루프의 검사기, retry: 같은 fix, gate: 그 루프의 게이트}
 (f) 처방 가지 노드가 루프 골격 칸(판정 · 바퀴 · 게이트)을 쓰지 않는다
 (g) 시험 뒤 라우터가 detour_limit 을 읽는다 · 시험지가 travel_graph 를 import 하지 않는다
 (h) 진단 뒤 라우터가 failure_kind · detour_limit 을 읽는다 — `킷 고정 ▼` 처방 가지 분기가 살아 있나
```

### (3) 처방 가지 하나 = 세 조각 (고정)

| 조각 | 자리 | 하는 일 |
| --- | --- | --- |
| 등록부 한 줄 | `travel_graph/detours/registry.py` | `{"kind": …, "loop": "A"\|"B", "title": …}` — 무엇을 · 어느 루프에서. **적힌 순서 = 진단 우선순위** |
| 모듈 | `travel_graph/detours/<이름>.py` | `fix()` 고치는 법(처방) · `inject()` 실패 재현 · `INJECT_AT` · `HOWTO`(게이트 '고치려면' 문장) |
| 시험지 | `scripts/detour_tests/test_<이름>.py` | `run(root)` → 검사기와 같은 `Result`. 종료 코드 0 합격 · 2 불합격 · 1 깨짐 |

세 조각은 한 명령이 한 번에 만듭니다. 이름(`kind`)이 곧 자리입니다.

```bash
python scripts/new_detour.py <이름> --loop A --title "사진 설명이 영어로 나옴"
```

**만든 직후에도 그래프는 그대로 돕니다.** 빈 시험지는 늘 합격이라 진단이 이 가지를 고르지
않고, 빈 `fix` 는 아무것도 바꾸지 않습니다. 그 상태에서 `check_graph_shape.py` 12행이 PASS 입니다.
`--loop B` 로 만들면 모듈이 처음부터 `INJECT_AT = "country"` 입니다 (이유는 (13)). 명령은 끝에 그 루프에
맞는 확인 명령(`--auto stop` 또는 `--auto proceed`)까지 출력합니다.

> 교육생이 "노드를 늘리는 것"은 여전히 금지입니다 — 정확히는 **루프 골격이나 진단에** 늘리는 것이
> 금지입니다. 노드는 이 명령(처방 가지)으로만 늘립니다. `build.py` · `edges.py` · `nodes.py` 는
> 건드리지 않습니다.

### (4) ★ 시험지 하나로 진단과 합격을 같이 봅니다 (고정)

```text
diagnose_*   그 루프의 시험지를 등록 순서대로 풀어 본다 → 불합격인 첫 처방 가지(한도 남은 것)를 고른다
test_<이름>  같은 시험지를 한 번 더 푼다(재검)          → 합격이면 복귀
```

진단 기준과 합격 기준이 다르면 **"진단은 문제라는데 시험은 합격"** 인 틈이 생기고, 그 틈에서
그래프가 같은 가지를 끝없이 돕니다. 한 파일이 두 역할을 하면 그 틈이 **구조적으로** 없습니다.

시험지는 **고치는 코드(`travel_graph/`)를 import 하지 않습니다.** 고치는 쪽이 채점표를 만들면
자기 오해를 스스로 통과시킵니다 — 검사기를 잠근 것과 같은 이유입니다. 시험지는
`scripts/detour_tests/_common.py` 와 `scripts/_contract.py` 만 씁니다.

> **두 말을 구분합니다.** **계약 검사기**(`scripts/check_*.py`)는 "계약을 채웠나"를 보는
> 루프 킷과 같은 자이고 여전히 만들지도 고치지도 않습니다. **처방 가지 시험지**
> (`scripts/detour_tests/test_<이름>.py`)는 "그 문제가 사라졌나"만 보며, STEP 6 에서만
> 교육생이 만듭니다. 킷의 시험지 셋(`test_encoding` · `test_image_dead` · `test_image_spec`)은 고치지 않습니다.

### (5) ★ 합격하면 그 루프의 검사기로 돌아옵니다 (고정)

```text
루프 A 처방 가지   합격 → check_information      수집 노드(collect_*)로 가지 않는다
루프 B 처방 가지   합격 → check_page             build_page 로 가지 않는다
```

두 가지 이유입니다.

- **판정 독립.** 시험지는 "그 문제가 사라졌나"만 봅니다. 계약을 채웠는가는 루프 골격의 검사기
  (루프 킷과 바이트 단위로 같은 파일)가 **다시** 잽니다.
- **합류가 영영 기다린다.** 합류가 `add_edge(["collect_country", "collect_city"], ...)` 라
  수집 노드 한쪽으로만 돌아가면 다른 쪽을 기다리며 **예외 없이 조용히 멈춥니다.**
  재수집이 `repair_*` 라는 별도 노드인 것과 같은 이유입니다.

### (6) 처방 한도 2회 · 바퀴를 쓰지 않습니다 (고정)

```text
detour_limit = 2        처방 한도 — 처방 가지 하나가 사람의 판단 없이 돌 수 있는 횟수
                        fix 1회째 → test 불합격 → fix 2회째 → test 불합격 → 게이트
                        (바퀴 상한 3 · 처방 한도 2 — 둘은 따로 센다)
```

- **처방 가지에서 합격하고 돌아온 방문은 바퀴(`loop_a_iter` · `loop_b_iter`)로 세지 않고**,
  '같은 오류 반복'도 올리지 않습니다. `history` 에 `(처방 가지에서 복귀 — 바퀴를 쓰지 않음)` 이 찍힙니다.
  세면 가지가 돌 때마다 재수집 기회가 하나씩 사라집니다. 루프판 비교표의 "반복 횟수"도
  그래서 같은 뜻으로 비교됩니다.
- 처방 한도를 다 쓰면 **그 루프의 게이트**에서 사람이 봅니다. 게이트 화면 `② 왜` 맨 앞에
  **"처방 가지가 못 고침 — <title>"** 줄이 뜹니다. 처방 한도를 다 쓴 실행은 사람 호출이 늘 수
  있습니다 — 그때는 적습니다. `② 왜` 의 처방 가지 줄은 세 종류입니다.

  ```text
  처방 가지가 못 고침 — <title>                  처방 한도를 다 썼다 · '고치려면' 칸은 모듈의 HOWTO
  처방 가지 시험지가 깨짐 — <title>              내 시험지가 실행 중에 멈췄다 — 증상이 아니다. 시험지를 혼자 돌려 오류 줄을 고친다
  처방 가지를 미룸 — <title> (정성 회차 중)      루프 B · 파일 해시 사슬 보호 ((8)). research · rebuild 면 다시 선다
  ```

  `fix()` · `inject()` 가 예외를 내도 그래프는 죽지 않습니다 — `fix` 는 `못 고침: fix() 가 실행 중에
  멈췄습니다 — …` 로, `inject` 는 `실패 재현 [<이름>] 이 멈췄습니다 — … (재현하지 못함)` 으로 history 에 남습니다.
- 게이트에서 사람이 `more`(A) · `research` · `rebuild`(B) 를 고르면 처방 가지 횟수가 0 으로
  돌아갑니다 (history `human_gate_a: 처방 한도를 새로 채웁니다` · `human_gate_b: 처방 한도를 새로 채웁니다`). 바깥 루프는 사람 소유입니다.

### (7) 원인을 먼저, 판정을 다음에 (고정)

```text
판정  info_verdict · page_verdict   검사기 노드가 쓴다    "기준을 채웠나"
원인  failure_kind                  진단 노드가 쓴다      "무엇이 터졌나 — 정해진 고칠 법이 있나"
```

라우터(`route_after_info` · `route_after_page`)는 두 칸을 나란히 읽습니다. 진단이 처방 가지를
골랐고 처방 한도가 남았으면 **판정이 PASS 여도** 가지로 갑니다 — 가지가 보는 실패(깨진 글자 ·
원본 크기 사진)는 검사기가 세지 않기 때문입니다. 이 분기는 `edges.py` 의

`failure_evidence`(증상 문장)는 게이트 화면용입니다. **라우팅에 쓰지 않습니다** — 자유 문장이기 때문입니다.

### (8) 정성이 돈 뒤에는 루프 B 처방 가지를 타지 않습니다 (고정)

정성 3회는 파일 해시로 사슬을 잇습니다. 그 사이나 그 뒤에 가지가 결과물을 고치면 사슬이 끊겨
루프 C 가 멈춥니다. 그래서 **정성(루프 C)이 한 회차라도 돈 뒤에는 `diagnose_page` 가 처방 가지를
고르지 않고** 증상만 게이트에 남깁니다. 게이트 B 에서 `research` · `rebuild` 를 고르면 정성
회차가 0 이 되므로 그때부터 다시 탈 수 있습니다.

### (9) 처방 가지는 데이터를 고칩니다 (고정)

`fix()` 가 받는 `data` 는 `country` · `days` · `country_intro` · `cities` 입니다. 이것을 **그 자리에서**
고치면 `nodes.fix_detour` 가 상태로 되올리고 파일(`output/research_data.json`)에도 씁니다.
루프 B 처방 가지는 화면도 다시 그립니다. **HTML 만 고치지 않습니다** — 다음 `build_page` 가 덮어씁니다
(`rebuilder` 와 같은 이유 · 같은 고칠 법).

### (10) 규칙 두 줄이 늘었습니다 — CLAUDE.md §8 의 9 · 10 (고정)

`check_graph_shape.py` 11번이 둘 다 자동으로 잡습니다. **하지 않는 것:**

### (12) 두 축 — `failure_type`(7종)과 `failure_kind`(처방 가지 이름) (고정)

STEP 3 의 실패 라우팅 7종(`failure_type`)은 루프에서 이식한 **넓은 분류**라 그대로 둡니다.
