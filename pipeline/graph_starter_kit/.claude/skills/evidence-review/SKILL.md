# evidence-review — 증거 정리와 비교

## 활성화 조건

그래프 실행이 끝난 직후, 또는 교육생이 결과를 묻거나 왜 멈췄는지 물을 때.

---

## 절대 규칙 5가지

1. **못 채운 칸을 숨기지 않는다.** 넘어갔더라도 보고서에 그대로 적는다.
2. **종료 코드가 근거다.** "잘 된 것 같습니다" 를 완료로 쓰지 않는다.
3. `live` 가 `replay` 로 폴백했으면 **반드시 적는다.**
4. 루프판 기준선은 `graph/04_RUN_EVIDENCE.md` 의 **「루프판 기준선」 절**에서 읽는다 — 킷에 든
   예시 인계본은 6번, 교육생이 루프 킷의 `export_graph_handoff.py` 로 직접 뽑은 인계본은 8번이다.
   칸에 `(기록 없음 …)` 이 적혀 있으면 교육생 본인의 루프 기록에서 옮기고, 그것도 없으면
   `(인계본에 없음)` 으로 적는다. **만들어 내지 않는다.** (`verify_all.py` 끝에도 같은 안내가 찍힌다)
5. 실측이 한 번뿐이면 **"한 번은 일화"** 라고 명시한다. 루프 골격 구조 변경을 권하지 않는다.
   이 규칙은 **킷에 넣을지**를 가르는 기준이다. **교육생 본인 킷에 처방 가지를 만드는 것은
   괜찮다** — 보고서 ③ · ③-2 에 뜬 `[후보]` · `[패턴 …]` 이면 STEP 6 의 재료가 된다
   (`[일화]` · `[한 번 …]` 뿐이면 아니다). 후보가 없으면 STEP 6 은 하지 않는다.
   킷의 기본 가지로 **편입**을 권하는 것은 서로 다른 실행 **3곳 이상**에서
   나온 것(`failure_report.py` 의 "패턴 — 킷 처방 가지 후보") 또는 원인과 고칠 법이 이미 알려진
   실패 축(예: 인코딩)뿐이다. 편입 판단은 강사가 여러 교육생의 기록을 모아서 한다
   (`python scripts/failure_report.py <폴더>…`).

---

## 실행 순서

1. 아래를 읽는다.
   - `output/travel_site.html` 존재 여부
   - `python scripts/verify_all.py --json` 결과
   - 최종 상태의 `history` (Studio 결과 패널, 또는 `run_once.py` 끝의
     `history — 검사기 · 진단 · 처방 가지 · 게이트 줄만`)
   - `graph/04_RUN_EVIDENCE.md` 의 「루프판 기준선」 절 (예시 인계본은 6번 · 직접 뽑은 인계본은
     8번 — 절대 규칙 4)
   - **실패 기록** — 진단 · 시험 노드가 `evidence/failures/<thread_id>.jsonl` 에 남긴 것.
     파일을 직접 읽지 말고 보고서로 읽는다.

     ```bash
     python scripts/failure_report.py          # 가장 최근 실행 하나
     python scripts/failure_report.py --all    # 이 킷의 실행 전부 (일화인지 패턴인지 볼 때)
     ```

     `run_once.py` 는 실행마다 새 thread(`run-YYYYmmdd-HHMMSS`)를 쓰므로 실패 기록도 실행마다
     한 파일이다. 인자 없이 돌리면 **가장 최근 파일 하나**만 읽는다 — 이번 실행 전체를 보려면
     그 실행의 파일을 넘기고(`python scripts/failure_report.py evidence/failures/<thread_id>.jsonl`),
     교육생 본인의 여러 실행을 모아 볼 때 `--all` 을 쓴다 (강사는 `<폴더>…` 로 여러 교육생 것을 모은다).

     보고서의 ① 실행별 요약 · ② 처방 가지가 맡은 실패 · ③ 아직 처방 가지가 없는 실패 ·
     ③-2 재수집(LLM)이 반복해서 맡은 원인이 아래 표 ④ · ⑤ 의 재료다. 기록이 없다고 나오면(exit 2)
     그대로 적는다.

     ```text
      ② 처방 가지가 맡은 실패
        image_dead       들어감 1번 · 시도 2번 · 합격 0번
                         (들어감 = 진단이 그 가지로 보낸 횟수 · 시도 = fix → test 를 돈 횟수, 재시도 포함)
      ③ 아직 처방 가지가 없는 실패 — 규칙표 밖 · 수집 실패 · 가지가 못 맡음 (같은 줄 2번 이상이면 후보 · 실행 3곳 이상이면 패턴)
        [일화] 실행 1곳 · 1번
           처방 가지 image_dead 가 못 고침 · 손으로 만들 수 없는 주소 형태입니다 (upload.wikimedia.org). …
      ③-2 재수집(LLM)이 반복해서 맡은 원인 — 처방 가지 후보 (같은 입력에 같은 고칠 법이 있으면 가지로)
        [후보] 루프 A 재수집(LLM) · <원인>
           실행 1곳 · 한 실행에서 최대 2바퀴 · 부족 합계 <N>곳
     ```

     ③ 의 출처(맨 앞 말)는 넷이다 — `규칙표에 없는 부족` · `수집 실패` · `처방 가지 <이름> 가 못 맡음`
     (진단이 증상을 봤지만 가지를 타지 않음 — 한도를 이미 다 씀 · 정성 회차 중 · 시험지가 멈춤) ·
     `처방 가지 <이름> 가 못 고침` (fix → test 를 한도까지 돌고도 불합격 → 게이트로 간 것).
     ③-2 는 가지 없이 SHORT 로 남아 재수집(LLM)으로 간 원인을 (루프, 원인)으로 묶어 센다 — 한
     실행에서 2바퀴 이상 또는 2실행 이상이면 `[후보]`, 3실행 이상이면 `[패턴 — 킷 처방 가지 후보]`,
     그 밖은 `[한 번 — 재수집이 맡으면 된다]`. 루프 B 줄의 머리표는 `재생성 · rebuilder(LLM)` 이다.
     ③ 도 같은 등급을 쓴다 — 한 번 `[일화]` · 같은 줄 2번 이상 또는 2실행 이상 `[후보]` · 3실행 이상 `[패턴 …]`.
     **replay 실행은 ③-2 에서, 재현(inject) 실행은 ③ · ③-2 둘 다에서 세지 않는다** (replay 의 재수집은
     LLM 이 아니라 인계본을 잘라 쓰고, 재현은 일부러 다시 일으킨 실패다 — `(재현(inject) 실행 N개는 …)` 한 줄이 뜬다).
     그래서 replay 기본 실행은 ③ · ③-2 가 모두 비는 것이 정상이고, 보고서 끝 줄이
     `이번 실행의 실패는 이미 처방 가지와 재수집이 맡았습니다 — STEP 6 은 하지 않아도 됩니다` 로 나온다.
     ③ 에 `[일화]` 뿐이면 `한 번 나온 실패(일화)뿐입니다 — STEP 6 은 하지 않아도 됩니다` 다.
     후보가 있으면 끝 줄이 `` 다음: 후보 하나를 골라 specs/06_DETOUR.md 의 `읽기 5` 에 적고 `STEP 6 진행해줘` `` 다.
2. `evidence/runs/<run_id>/` 에 기록을 남긴다.
3. 아래 표(① ~ ⑤)를 만든다.
4. 다음 행동 선택지를 준다.

## 표 ① 실행 요약

```text
상태        : SUCCESS | HALT_RESEARCH_GAP | HALT_NEEDS_HUMAN | HALT_ENVIRONMENT
실행 모드   : live | replay | live→replay 폴백
thread_id   : ...
루프 A      : N바퀴  판정 <...>
루프 B      : N바퀴  판정 <...>
루프 C      : N/3회  판정 <...>   ← 고치지 못한 위반은 목록으로 적는다
게이트      : A=<...>  B=<...>  C=<...>   ← 처방 가지가 한도를 다 써 게이트에 더 섰으면 그 정지도 적는다
                                          (예: A=more(처방 가지 image_dead 한도 끝) → A=proceed)
처방 가지   : 결과까지 적는다. 없으면 "타지 않음"
              예) image_dead 1회 → PASS → check_information 복귀   (재현: image_dead)
                  image_spec 2/2회 FAIL → 게이트 B                  (재현: image_spec)
              실패를 재현한(inject) 실행이면 "(재현: <이름>)" 를 붙인다 — 저절로 난 실패인 척하지 않는다
실패 기록   : evidence/failures/<thread_id>.jsonl
구조 검사   : exit <...>
최종 검증   : exit <...>
못 채운 칸  : (목록. 없으면 "없음")
```

## 표 ② 루프판 vs 그래프판 — 이 실습의 결론

루프판 칸의 숫자는 예시 인계본(`graph/04_RUN_EVIDENCE.md` 6번 「루프판 기준선」)의 값이다. 직접 뽑은
인계본이면 그 파일 8번 「루프판 기준선」의 값으로 바꾸고, `(기록 없음 …)` 칸은 본인 루프 기록에서,
그것도 없으면 `(인계본에 없음)` 으로 둔다 (절대 규칙 4).

| | 루프판 | 그래프판 | 왜 달라졌나 |
| --- | --- | --- | --- |
| 반복 횟수 | 8 (A 3 · B 2 · C 3) | | 처방 가지는 **바퀴로 세지 않는다** → 같은 뜻으로 비교된다 |
| 전체 시간 | 약 40분 | | **병렬** |
| 실패 후 재실행 범위 | 바퀴 전체 | | **체크포인트** |
| 사람 호출 횟수 | 2 | | **3 이 정상** — 게이트 A 1 · B 2 (루프판 2 에 **정성 뒤 확정**이 하나 더). 처방 가지가 한도를 다 쓰면 그 루프의 게이트에 서고, 거기서 `more` · `research` · `rebuild` 를 고르면 같은 게이트에 한 번 더 선다 (그런 정지 하나마다 +1). 늘어난 수와 이유를 적는다. 실패를 재현한 실행이면 기본 실행과 섞지 않는다 |
| 정성 회차 | 3 / 3 | | **고정 예산 — 빨라지지 않는다** |
| `verify_all` | exit 0 | | **같은 검사기** |
| 못 채운 칸 | 0건 | | **같아야 정상.** 다만 **주소가 틀려서** 못 채운 칸(image_dead)은 처방 가지가 줄일 수 있다 |
| 계약 밖 아쉬움 | 1건 | | 검사기가 세지 않는 사람 메모다 (`graph/04_RUN_EVIDENCE.md` 5번) — 못 채운 칸에 섞지 않는다 |

반드시 덧붙일 한 줄:

> **못 채운 칸이 같다는 것이 중요합니다.** 그래프로 옮긴다고 인터넷에 없는 사진이
> 생기지 않습니다. 그래프가 개선하는 것은 실행 효율과 복구 능력입니다.
> 복구 능력의 예가 규칙 처방 가지입니다 — **주소가 틀려서** 못 채운 칸은 처방 가지가 정해진 절차로
> 줄일 수 있습니다. 있던 사진의 주소를 바로잡는 것이지, 없던 사진이 생기는 것은 아닙니다.

정성 회차 줄에는 한 줄 더 붙인다.

> **정성 3회는 그래프에서도 빨라지지 않습니다.** 회차가 서로의 결과 위에 쌓이므로
> 순차가 강제됩니다. 그래프의 이득은 루프 A(도시별 병렬)와 부분 재실행에서 나옵니다.

## 표 ③ 정성 회차 요약 (`evidence/runs/<run_id>/quality/`)

| 회차 | 렌즈 | 위반 | 고침 | 못 고침 (이유) | 재검증 |
| --- | --- | --- | --- | --- | --- |
| 1 | 내용이 실한가 | | | | exit |
| 2 | 실행 가능·사실인가 | | | | exit |
| 3 | 독자 관점에서 완결인가 | | | | exit |

`못 고침` 칸은 `passN.json` 의 `skipped_fix` 에서 그대로 옮긴다. **비워 두지 않는다.**

## 표 ④ 처방 가지 요약 (`failure_report.py` ② · history 의 `fix_*` · `test_*` 줄)

| 처방 가지 | 루프 | 들어감 N번 · 시도 N번 | 합격 (N번) | 못 고친 것 (게이트 `② 왜` · 실패 기록 원문) |
| --- | --- | --- | --- | --- |
| `encoding` 글자가 깨짐 | A | | | |
| `image_dead` 이미지 주소가 죽어 있음 | A | | | |
| `image_spec` 사진이 화면 규격에 안 맞음 | B | | | |

- `들어감` 은 진단이 그 가지로 보낸 횟수, `시도` 는 fix → test 를 돈 횟수(재시도 포함)다 —
  `failure_report.py` ② 의 `들어감 N번 · 시도 N번 · 합격 N번` 을 그대로 옮긴다.
- `replay` · 재현 없음이면 전부 `0 · — · 없음` 이 정상이다. **진단은 매번 돌았다**는 것만 적는다
  (history 의 `diagnose_*: 처방 가지 대상 없음 → 루프 골격 그대로`). `live` 는 실제로 모은 주소가
  죽어 있으면 재현 없이도 켜진다 (킷의 예시 인계본 `graph/04_RUN_EVIDENCE.md` 1-b 의 404 가 그런
  경우다 — 직접 뽑은 인계본에는 이 절이 없다) — 그대로 적는다.
- 실패를 재현한(inject) 실행이면 줄 끝에 `(재현: <이름>)` 을 붙인다.
- 합격하고 돌아온 방문은 **바퀴로 세지 않는다.** history 의
  `(처방 가지에서 복귀 — 바퀴를 쓰지 않음)` 을 근거로 표 ② 의 반복 횟수와 섞지 않는다.
- 한도를 다 쓴 가지는 `못 고친 것` 칸을 **비워 두지 않는다.** 게이트 `② 왜` 의 줄 종류
  (`처방 가지가 못 고침` · `처방 가지 시험지가 깨짐` · `처방 가지를 미룸 … (정성 회차 중)`)와, 게이트에서
  사람이 무엇을 골랐는지(`more` · `proceed` · `done` …)도 함께 적는다. 그 정지는 표 ① 의 `게이트`
  줄과 표 ② 의 사람 호출에도 들어간다.
- STEP 6 에서 교육생이 만든 가지가 있으면 줄을 더한다 (`travel_graph/detours/registry.py` 순서대로).

## 표 ⑤ 처방 가지 후보 (STEP 6 진입 조건 · `failure_report.py` ③ · ③-2)

| 실패 (패턴 · 원인) | 어디서 나왔나 | 실행 몇 곳 · 몇 번 (③-2 는 최대 바퀴) | 판정 | 예 |
| --- | --- | --- | --- | --- |
| | ③ 규칙표에 없는 부족 · 수집 실패 · 처방 가지 <이름> 가 못 맡음 · 처방 가지 <이름> 가 못 고침 | | 일화 / 후보 / 패턴 — 킷 처방 가지 후보 | |
| | ③-2 루프 A 재수집(LLM) · 루프 B 재생성 · rebuilder(LLM) | | 후보 / 패턴 — 킷 처방 가지 후보 / 한 번 — 재수집이 맡으면 된다 | |

- 보고서의 판정을 **그대로** 옮긴다. ③ 은 한 번이면 `일화`, 같은 줄 2번 이상 또는 2실행 이상이면
  `후보`, 서로 다른 실행 3곳 이상이면 `패턴 — 킷 처방 가지 후보`.
  ③-2 는 한 실행에서 2바퀴 이상 또는 2실행 이상이면 `후보`,
  3실행 이상이면 `패턴 — 킷 처방 가지 후보`, 그 밖은 `한 번 — 재수집이 맡으면 된다`. 판정을 올려 적지 않는다.
- ③ · ③-2 의 `[후보]` 가 교육생 본인 킷의 STEP 6 재료다 — 킷에 넣을 `[패턴 …]`(3실행 이상)까지 기다리지
  않는다. `[일화]` · `[한 번 …]` 뿐이면 아직 재수집 · 게이트에 둔다 (절대 규칙 5 — 한 번은 일화).
  단 **같은 입력에 같은 고칠 법이 있을 때만** 가지로 뺀다 — 없으면 아직 재수집(LLM)에 둔다.
- 실패를 재현(inject)한 확인 실행의 줄은 보고서가 ③ · ③-2 에서 **이미 빼고** 센다 — 일부러 다시 일으킨
  실패다. 같은 줄이 재현 없는 실행에서 되풀이될 때 후보다.
- `처방 가지 <이름> 가 못 고침` 은 한도를 다 쓰고 게이트로 간 가지의 증상이다 — 표 ④ 의
  `못 고친 것` 과 같은 사건이다. 새 가지 재료라기보다 **그 가지의 fix 를 고칠 재료**다.
- ③ · ③-2 가 모두 비어 있으면 "없습니다 — 이번 실행의 실패는 이미 처방 가지와 재수집이
  맡았습니다. STEP 6 은 하지 않아도 됩니다" 라고 적는다. `[일화]` 뿐이면 "한 번 나온 실패(일화)뿐 —
  STEP 6 은 하지 않아도 됩니다" 라고 적는다. replay 기본 실행은 둘 다 비는 것이 정상이다
  (replay 는 ③-2 에서 세지 않는다). 후보는 live 실행 · `--all` · 여러 교육생의 기록을 모은 폴더에서 생긴다.

## 다음 행동 선택지

```text
[1] 나라를 바꿔 한 번 더 돌린다       → 실측이 패턴인지 확인 (한 번은 일화, 세 번은 패턴)
[2] 게이트에서 다른 답을 골라 본다    → 같은 thread 를 fork 하면 그 지점부터 다시
[3] 후보 하나를 처방 가지로 뺀다      → STEP 6 (graph-detour-builder). 표 ⑤ 에 후보가 있을 때만
[4] 여기서 마친다                     → PROJECT_MEMORY.md 6번 비교표를 채우고 끝
```

**`[3]` 은 표 ⑤(보고서 ③ · ③-2)에 후보가 있을 때만 보여 준다.** 비어 있으면 `[3]` 을 빼고
"STEP 6 은 하지 않아도 됩니다"라고 한 줄 적는다 — 가지를 만들려고 없는 실패를 찾지 않는다.

`[3]` 은 루프 골격을 고치는 것이 아니다. 루프 골격 14개와 진단 2개는 그대로 두고, 진단 노드에서
갈라지는 처방 가지(fix → test → 검사기로 복귀)를 **하나 더** 붙인다. 루프 골격이나 진단에 노드를
늘리는 것은 여전히 하지 않는다.
