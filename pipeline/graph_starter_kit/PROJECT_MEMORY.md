## 1. 이 실습의 전제

<!-- PROJECT:BEGIN -->

```text
그래프는 루프의 상위 개념이 아니다. 옆으로 넓히는 확장이다.

  얻는 것                        치르는 대가
  ① 병렬                        ① 상태를 명시적으로 선언해야 한다
  ② 부분 재실행 · 되감기          ② 노드가 서로를 몰라야 한다
  ③ 구조가 눈에 보인다            ③ 간선 조건을 코드에서 빼야 한다
  ④ 실패가 가지가 된다 (규칙 처방 가지)
     추적 · 확장 · 재현 — 가지는 진단에서만 난다 (그 자리는 킷이 잠가 둔다)
     반복되는 실패를 로그를 따라 가지로 키운다 — 새 가지는 로그에 후보가 있을 때만 (STEP 6)

이 넷이 필요 없으면 루프가 더 낫다.
루프 골격 14개짜리 순차 그래프는 while 문보다 코드가 세 배 길다.
```

## 2. 킷이 미리 정해 둔 것과 그 이유

| 정한 것 | 값 | 왜 |
| --- | --- | --- |
| 노드 수 | **루프 골격 14개 고정 · 처방 가지로만 늘림** (지금 22개 = 루프 골격 14 + 진단 2 + 규칙 처방 가지 3×2) | 루프 골격을 더 늘리면 1시간 실습에서 그림이 안 읽힌다. 늘리는 것은 **문제가 난 지점에서만** — 진단 노드에서 갈라지는 처방 가지. 22개가 됐어도 하위 그래프로 접지 않고 평평하게 둔다: **처방 가지에 불이 켜지는 것이 그대로 보여야 한다** (2026-09-27 개정 — 전에는 "14개") |

| 재수집 응답은 patch | 경로+값 | 전체 JSON 재타이핑은 멀쩡한 칸을 지운다 |

| 재수집은 수집 노드 재사용이 아니라 별도 노드 | 구조 제약 | 합류(`add_edge([a,b],c)`)에 되돌이 간선을 걸면 **예외 없이 조용히 멈춘다.** 최소 재현으로 확인함 |
| 루프 골격 배선(`build.py`) 고정 · 처방 가지는 등록부 한 줄 | 킷 제공 · `travel_graph/detours/registry.py` | 배선을 손으로 짜면 30분이 사라진다. 처방 가지는 한 줄 등록하면 노드 둘(`fix_<이름>` · `test_<이름>`)과 간선 셋(back · retry · gate)이 **같은 모양으로** 생긴다 — 모양이 하나라 틀릴 곳이 없고, 구조 검사 11번(처방 가지 계약)이 그 모양을 잠근다 |

| 검사기 3개 복사 | 바이트 단위 동일 | 루프판과 같은 자로 재기 위해 |
| 계약 읽는 위치만 변경 | `_contract.py` | `MASTER_SPEC.md` → `graph/03_CONTRACT.json` |
| 체크포인터 미주입 | `compile()` | Studio 의 Agent Server 가 담당한다 |
| 게이트 2개 분리 | `human_gate_a` / `_b` | **선택지가 다르다.** 한 노드면 어디서 왔는지 상태에 또 적어야 한다 |
| `cities` 는 upsert reducer | `merge_cities` | `repair_city` 가 같은 도시를 다시 준다. `add` 면 중복이 쌓인다 |
| `city_failures` 도 upsert | `merge_failures` | 재수집에 성공하면 **기록이 사라지는 것**으로 표현한다 |

| **`quality_pass` 는 reducer 없음** | 단일 정수 | **회차 카운터는 누적이 아니라 덮어쓰기.** 붙이면 2회차에 1+2=3 이 되어 한 회차를 건너뛴다 (정성 2회만 돈다) |
| **정성 회차 3회** | 킷 고정 | 점수로 닫으면 글 쓴 쪽이 자기 글에 점수를 준다 |
| **정성은 순환으로 3회** | 노드 하나 | 정적 간선 3개면 병렬이 되어 해시 사슬이 끊긴다 |
| **게이트 B 재사용** | 노드 추가 없음 | 정성 전/후 질문이 같은 자리다. 회차 칸으로 구분한다 |
| **이미지 확인은 코드가** | `research.verify_asset()` | 모델에게 `verified` 를 적게 하면 그것마저 지어낸다 |
| **진단은 검사기 뒤 별도 노드** | `diagnose_info` · `diagnose_page` (결정론) | **판정**(기준을 채웠나)과 **원인**(무엇이 터졌나)은 다른 일이다. 검사 스크립트는 루프판과 바이트 단위로 같아야 해서 원인을 넣을 자리가 없다. 라우터는 원인을 먼저, 판정을 다음에 읽는다 — 판정이 PASS 여도 검사기가 세지 않는 결함(깨진 글자 · 규격 밖 사진)이 있기 때문 |
| **처방 가지는 "정해진 고칠 법이 있는 문제"만** | 결정론 `fix` | 죽은 사진 주소는 재수집(LLM)에 다시 맡기면 같은 식으로 지어낸다(킷에 든 예시 인계본 `04_RUN_EVIDENCE` 1-b — 루프 킷이 실제로 겪은 실측. `export_graph_handoff.py` 로 뽑은 내 인계본에는 이 절이 없다). 절차로 고칠 수 있는 것만 처방 가지로 빼고, 나머지는 아직 재수집(LLM) · 게이트에 둔다 — 같은 실패가 로그에서 반복되고 고칠 법이 정해지면 가지로 뺀다(그래프가 자라는 방향) |
| **킷 기본 가지 3개는 알려졌거나 로그로 잡힌 실패** | encoding · image_dead · image_spec | encoding = 원인과 고칠 법이 이미 알려진 실패 축(Windows cp949 · 현지 글자 파일명)이라 로그 실측 전에 미리 구축 · image_dead = 루프 킷 실행 로그(해시 두 글자 `8/8c` 를 지어내 11장 전부 죽음, 킷에 든 예시 인계본 `graph/04_RUN_EVIDENCE.md` 1-b — 재수집(LLM)으로는 또 지어냄) · image_spec = 실습생 게이트 입력(원본 크기 사진이 서랍을 뚫음, 검사기는 못 봄). 셋 다 그래프 안에서 늘 돈다 — 진단은 매번, 가지는 그 실패가 났을 때만 |
| **킷에 가지를 넣는 규칙** | 반복 확인 **또는** 알려진 실패 축 | 로그에서 반복 확인된 실패(한 번은 일화, 세 번은 패턴 — 여러 교육생 기록에서 서로 다른 실행 3곳 이상) 또는 원인과 고칠 법이 이미 알려진 실패 축(예: 인코딩). (킷 기본 셋 가운데 image_dead 는 두 실행, image_spec 은 게이트 입력 한 번에서 나왔다 — 킷 저자가 보기로 넣은 예외다) 교육생의 가지는 본인 킷에만 둔다 |
| **STEP 6 은 조건부** | 보고서 ③ · ③-2 에 후보가 있을 때만 | 일부러 준 실패로 하는 실습이 아니다. 새 실패가 로그에 반복해서 남을 때만 같은 방식으로 가지를 더한다 — 후보 없이 만들면 없는 실패를 지어내게 된다. replay 기본 실행은 ③ · ③-2 가 비는 것이 정상. 시간은 STEP 1~5 + 실행 약 60분, STEP 6 은 후보가 있을 때만 약 20분 (2026-09-28 개정 — 전에는 모든 교육생이 STEP 6 을 했다) |
| **보고서 ③-2 (재수집이 반복해서 맡은 원인)** | 진단 기록 `causes` · `loop_iter` | 원인 규칙표 끝의 포괄 규칙에 걸린 부족은 '그 밖'이 아니라 ③ 에 절대 안 뜬다 — 재수집(LLM)이 몇 바퀴를 돌아도. 토큰을 쓰며 되풀이되는 그 실패가 바로 가지 후보라 따로 센다. replay 실행은 세지 않는다 (인계본을 잘라 쓰는 재수집이라 가짜 패턴이 된다) |
| **시험지 하나로 진단과 합격** | `scripts/detour_tests/test_<이름>.py` | 진단용과 합격용을 따로 두면 "진단은 문제라는데 시험은 합격"인 틈이 생긴다. 하나면 구조적으로 없다. 시험지는 고치는 코드를 import 하지 않는다 (판정 독립) |
| **처방 가지는 검사기로 복귀** | `back` → `check_information` · `check_page` | 수집 노드로 돌아가면 합류가 영영 기다린다. 그리고 시험지는 "그 문제가 사라졌나"만 보므로 계약은 루프판과 같은 검사기가 다시 잰다 |
| **복귀 방문은 바퀴를 쓰지 않음** | `detour_verdict` PASS 면 `*_iter` 그대로 | 바퀴는 검사 횟수다 (첫 수집 1, 재수집 · 재생성마다 +1). 처방 가지까지 세면 루프판 비교표의 "반복 횟수"가 다른 뜻이 된다. 처방 가지는 자기 한도(처방 한도 `detour_limit` 2)를 따로 갖고, 다 쓰면 그 루프의 게이트로 간다 (바퀴 상한 3 · 처방 한도 2) |
| **정성 중에는 루프 B 처방 가지 금지** | `diagnose_page` 가 증상만 남김 | 정성 3회는 파일 해시로 사슬을 잇는다. 그 사이나 뒤에 처방 가지가 파일을 고치면 사슬이 끊겨 루프 C 가 멈춘다. 게이트 B 에서 `research` · `rebuild` 로 정성 회차가 0 이 되면 다시 탄다 |
| **처방 한도는 사람이 새로 채움** | `more` · `research` · `rebuild` → `detour_attempts` `{}` | 바깥 루프는 사람 소유다. 사람이 "한 번 더"를 고른 뒤에는 데이터가 바뀌었으니 처방 가지도 다시 설 수 있어야 한다 |
| **실패 기록은 `evidence/failures/`** | `<thread_id>.jsonl` · 진단 · 시험 노드가 한 줄씩 | `evidence/runs/` 의 이름순 마지막 폴더를 정성 판정기가 "이번 실행"으로 읽는다. 거기에 폴더를 만들면 루프 C 가 엉뚱한 폴더를 읽는다 |

## 3. 실행 모드를 두 개 둔 이유

<!-- PROJECT:BEGIN -->

```text
live     기본값. claude -p 로 실제 조사. 그래프의 병렬 이득이 진짜로 측정된다
replay   graph/research_data.json 에서 잘라 씀. 10초. 결과가 항상 같다

replay 는 '가짜'가 아니다. 루프 킷이 실제로 모은 원본 데이터다.
바뀌는 것은 **누가 그 데이터를 가져오는가**뿐이고,
그래프 구조 · 라우터 · reducer · 게이트는 완전히 같은 코드가 돈다.

replay 첫 바퀴에는 일부러 계약을 덜 채운다 (마지막 관광지의 이미지를 뺀다).
루프 A가 최소 한 바퀴는 돌아야 라우터가 일하는 것을 눈으로 볼 수 있기 때문이다.
GRAPH_REPLAY_FULL=1 로 끌 수 있다.

이 '이미지 한 장 빼기'는 처방 가지를 켜지 않는다. **없는** 사진이라 루프 골격의 재수집이
채운다 — 처방 가지(image_dead)는 **주소가 틀린** 사진을 맡는다. 그래서 이미 있는 가지가
켜지는 것을 보려면 그 실패를 따로 재현한다. 실패 재현(inject)은 모드가 아니라 입력 칸이고, 평소 비운다.

  원인 묶기: 검사기의 요약 줄 `…: 목표 살아 있는 이미지 1 / 실제 부족` 은 **없는 사진에도 죽은
  사진에도 똑같이** 붙는다 (검사기 문구라 잠김). 그래서 `nodes.classify` 는 같은 칸에
  `url 이 없습니다` 가 있으면 그 줄도 "이미지를 아직 안 모음"으로 센다 — 재현 없는 replay
  첫 바퀴는 "이미지를 아직 안 모음 9 / 9". "이미지 주소가 죽어 있음"은 주소가 있는데 열리지 않는
  사진뿐이다. 처방 가지가 켜지는지는 이 묶음이 아니라 진단(image_dead 시험지)이 정한다.

  Studio   {"inject": ["image_dead"]}
  터미널   python scripts/run_once.py --mode replay --inject image_dead --auto stop   (쉼표로 여럿)
           루프 B 까지(image_spec 등)는 --auto proceed — 게이트 B 에서 스스로 멈춘다

image_dead 재현은 실측 그대로다 — 첫 도시 두 번째 관광지 사진 주소를, 파일은 실재하고
해시 두 글자(8/8c)만 지어낸 upload.wikimedia.org thumb 주소 + 404 로 바꾼다. 고치는 법
1회째가 그것을 해시가 필요 없는 Special:FilePath/<파일>?width=1024 로 다시 쓴다.

replay 에서 재현이 없으면 처방 가지는 한 번도 켜지지 않는다. 진단 노드만 매번 켜진다.
(live 에서는 진짜 실패가 재현 없이도 처방 가지를 켠다.)
루프 A 가지는 첫 도시에서 재현하지만, image_spec 은 국가 소개 대표 사진에서 재현한다 —
replay 에서 루프 A 재수집이 도시를 통째로 되돌려 도시에서 재현한 실패가 지워지기 때문이다.
처방 가지도 replay 에서는 네트워크를 쓰지 않는다 (image_dead 의 live 만 실제로 열어 본다).
재현한 실행은 보고서에 재현했다고 적는다.

**루프 C(정성)만은 replay 에서도 실제로 판정한다.** 수집은 잘라 쓰더라도
정성 판정을 모의로 통과시키면 "고친 척"을 자동화하는 셈이 되기 때문이다.
그래서 replay 실행도 정성 3회에 6~12분이 든다. `claude` 를 부르지 못하면
조용히 통과시키지 않고 `blocked.json` 을 남겨 `check_quality` 가 ERROR 를 낸다.
```

## 6. 루프판과 비교

<!-- PROJECT:BEGIN -->

| | 루프판 (기준선) | 그래프판 | 차이의 원인 |
| --- | --- | --- | --- |
| 반복 횟수 | 5 (A 1 · B 1 · C 3) | **6** (A 2 · B 1 · C 3) | 처방 가지는 바퀴로 세지 않는다 — 같은 뜻으로 비교된다 |
| 전체 시간 | 약 22분 | **약 14분** (제출 → 정성 3회차 기록. 사람 대기 포함 · 루프판은 에이전트가 직접 작성한 시간이라 공정한 비교가 아님) | 병렬 |
| 실패 후 재실행 범위 | 바퀴 전체 | **지적된 도시만** (고베 6곳 patch, 오사카는 그대로) | 체크포인트 |
| 사람 호출 횟수 | 3 | **3** (A 1 · B 2) | **3 이 정상** — 게이트 A 1 · B 2 (루프판 2 에 **정성 뒤 확정**이 하나 더). 처방 가지가 처방 한도를 다 써 게이트가 더 섰으면 늘어난 수와 이유를 적는다 |
| 정성 회차 | 3 / 3 | **3 / 3** (위반 7 · 수정 17) | **고정 예산 — 같아야 정상** |
| `verify_all` | exit 0 | **exit 0** | 같은 검사기 |
| 못 채운 칸 | 0건 | **0건** | **같아야 정상** — "인터넷에 없는 정보"는 그대로다. 다만 **주소가 틀려서** 못 채운 칸(image_dead)은 처방 가지가 줄일 수 있다 |
| 계약 밖 아쉬움 | (인계본에 없음) | 아리마 온천이 "많이 걷기 싫다"·마라톤 조건에 맞는지는 사람이 판단 | 검사기가 세지 않는다 — 사람이 보고서에 적는다 |
| 처방 가지 (원인별로 다른 길) | 없음 — 모든 실패가 "한 바퀴 더" | **encoding 1회 PASS** (live) · image_dead · image_spec 은 타지 않음 | 진단 → 처방 가지. replay 에서 재현이 없으면 0회 |

> 정성 회차는 **빨라지지 않습니다.** 순차가 강제되기 때문입니다.
> 그래프의 이득은 루프 A(도시별 병렬)와 부분 재실행에서 나옵니다.
> 그리고 **복구 능력**에서 나옵니다. 주소가 틀려 못 채운 칸을 처방 가지가 정해진 절차로
> 줄이는 것이지, 없던 사진이 생기는 것이 아닙니다. 인터넷에 없는 정보는 그대로 못 채웁니다.
> 처방 가지는 바퀴로 세지 않으므로 '반복 횟수'는 루프판과 같은 뜻으로 비교됩니다.
> 실패를 재현한 실행의 숫자를 적었다면 그렇다고 밝힙니다 — 재현한 실패는 그 실행에서 저절로 난 실패가 아닙니다.

루프판 기준선은 `graph/04_RUN_EVIDENCE.md` 의 **「루프판 기준선」 절**에서 옵니다 — 킷에 든 예시
인계본은 6번, 루프 킷의 `export_graph_handoff.py` 로 뽑은 내 인계본은 8번입니다. 칸에 `(기록 없음 …)`
이 적혀 있으면 내 루프 기록에서 옮깁니다.
