# CLAUDE.md — 이 프로젝트의 운영 계약

이 파일은 소개가 아니라 **최상위 운영 규칙**이다.
자세한 절차는 Skill과 `specs/` 문서에 있다. 여기에는 라우팅 규칙과 절대 규칙만 둔다.

---

## 1. 프로젝트 목적

교육생이 **결정 21개**에 답해 STEP 1~7 명세를 완성하고, 그 명세를 근거로 **검증 가능한 루프 세 개**를 실행한다.
세 번째 루프(루프 C · 정성 완성도)는 **킷 고정**이라 결정이 늘어나지 않는다.
결과물은 `output/travel_site.html` 파일 하나다.

---

## 2. 세션 시작 시 읽는 순서

1. `CLAUDE.md` (이 파일)
2. `PROJECT_MEMORY.md`
3. `specs/00_INDEX.md` → `specs/00_DECISION_LOG.md`
4. 지금 다루는 STEP 문서
5. 루프 실행 모드라면: `MASTER_SPEC.md` → `LOOP_CONTRACT.md` → `USER_REQUEST.md` → `state/loop_state.json`

전부 읽지 못했으면 그렇다고 말한다. 읽은 척하지 않는다.

---

## 3. 두 가지 모드

| 모드 | 언제 | 무엇을 하는가 | 담당 Skill |
| --- | --- | --- | --- |
| **STEP 진행 모드** | STEP 7이 `APPROVED`가 되기 전 | 질문하고, 답을 받고, 명세를 채운다 | `step-spec-builder`, `spec-sync` |
| **루프 실행 모드** | STEP 7 승인 + 준비도 `READY` 이후 | 실제 구현 루프를 돈다 | `loop-run`, `evidence-review` |

**두 모드를 섞지 않는다.** STEP 진행 모드에서는 구현 코드를 만들지 않는다.

### 스킬 4개 — 언제 부르고, 끝나면 어디로 넘기나

| Skill | 부르는 신호 | 하는 일 | 끝나면 넘기는 곳 |
| --- | --- | --- | --- |
| `step-spec-builder` | "STEP N 진행해줘" | 질문 2~4개 → 명세 채움 → `validate_specs` | 다음 STEP · STEP 7이면 `loop-run` |
| `spec-sync` | "D-도시수를 바꾸고 싶어" · `REVISE_SPEC` | 영향 범위 계산 → 문서·계약·구조도 동기화 → 재잠금 | 원래 있던 곳(`step-spec-builder` 또는 `loop-run`) |
| `loop-run` | "루프를 실행해줘" · "이어서 돌려줘" | 루프 A → 되물음 → 루프 B → 되물음 → 루프 C 3회 → 최종 검증 | 종료되면 `evidence-review` |
| `evidence-review` | 루프 종료 직후 · "왜 멈췄어?" | 증거 정리 → 보고서 → **그래프 인계본** → 되물음 선택지 제시 | 사람의 답에 따라 `loop-run` 또는 `spec-sync` |

```text
step-spec-builder ──STEP 7 승인──▶ loop-run ──종료──▶ evidence-review
        ▲                            │  │                    │
        │                     REVISE_SPEC │              사람이 고름
        │                            ▼  │                    │
        └────────────────────── spec-sync ◀──────────────────┘
                                     │
                              재잠금 후 복귀
```

**전체 루프 구조도**는 `specs/00_DECISION_LOG.md`의 **5번**에 있다.
5-1 큰 그림 · 5-1b 한 바퀴 안쪽 · 5-1c 루프 C · 5-2 실패 라우팅 · 5-3 결정이 조종하는 자리 · 5-4 그래프 대응.

## 4. 루프는 셋이다. 순서는 고정이다

```text
루프 A  정보량 충족   →  scripts/check_information_count.py
   │                     명세한 개수·분량·중복·이미지 유효성
   │  (통과해야 다음)
   ▼
루프 B  페이지 완성   →  scripts/check_page_contract.py
   │                     그 정보로 화면 칸을 빠짐없이 채웠는가
   │  (통과해야 다음)
   ▼
루프 C  정성 완성도   →  scripts/check_quality_passes.py
                        규율 10가지로 3회 점검하고 실제로 고쳤는가
```

- **앞 루프가 통과하기 전에는 뒤 루프를 판정하지 않는다.** `scripts/verify_all.py`가 강제한다.
- 각 루프가 끝나면 **되물음**을 띄워 사람의 답을 받는다.
- **루프 C만 모양이 다르다.** 통과선이 아니라 **정해진 3회**로 닫는다.
  품질에 점수를 매기면 글을 쓴 쪽이 자기 글에 점수를 주게 되어 판정 독립이 무너지기 때문이다.
  그래서 판정기는 **품질이 아니라 절차**를 본다.

## 5. 검사기는 킷 소유다. 절대 만들지도 고치지도 않는다

```text
scripts/check_information_count.py   루프 A 판정기
scripts/check_page_contract.py       루프 B 판정기
scripts/check_quality_passes.py      루프 C 판정기
scripts/verify_all.py                최종 스위치 (A → B → C)
scripts/selftest/run_selftest.py     **판정기를 판정한다**
```

**채점표가 살아 있는지 먼저 본다.** 판정기가 조용히 약해진 것은 판정기가 알려
주지 않는다. 계약에 배치를 선택지 문구("우측 툴바")로 적었더니 **검사행 6개가
사라졌는데 판정은 PASS** 였던 일이 실제로 있었다. 그래서 검사행마다 그것을
반드시 빨간불로 만드는 최소 입력을 하나씩 두고, 루프를 시작하기 전에 돌린다.

```text
python scripts/selftest/run_selftest.py     exit 0 이어야 루프를 시작한다
```

`check_loop_readiness.py` 가 이것을 자동으로 돌린다. `exit 1` 이면 그것은
**결과물이 아니라 판정기의 문제**이므로 사람에게 넘긴다.

`scripts/export_graph_handoff.py`는 판정기가 아니라 **인계본 생성기**다.
루프가 끝난 뒤 `output/graph/`를 만든다. 이것도 킷 소유이므로 고치지 않는다.

- 이 파일들은 **이미 완성되어 있다.** 새로 만들지 않는다.
- 통과가 안 된다고 **검사기를 고치지 않는다.** 통과할 만큼 결과물을 고친다.
- 기준 숫자는 `MASTER_SPEC.md`의 `count_contract` · `page_contract` · `quality_contract`에서 읽는다.
  글자 수 하한, 중복 상한, 이미지 규칙, 정성 회차 수까지 **전부 그 파일에 있다.**
  기준을 바꾸려면 **명세를 바꾼다.** 스크립트를 건드리지 않는다.

> AI가 채점표를 직접 만들면 자기 오해를 스스로 통과시킨다. 그래서 채점표를 잠갔다.

## 6. `STEP N 진행` 요청을 처리하는 절차

0. 명세 확정을 위한 질문은 턴 도중 리버스 퀘스천을 통해 묻고, 피드백을 받아서 적용한다. 
1. 앞 STEP의 승인된 결정을 읽는다. 승인되지 않았으면 알리고 계속할지 묻는다.
2. 그 STEP의 목적을 **3줄 이내**로 설명한다.
3. `읽기 3`(이미 정해 둔 것)을 **요약해서 먼저 알려 준다.** 고민할 필요 없다는 것을 분명히 한다.
4. `읽기 4`의 질문을 **2~3개씩만** 제시한다. 선택지 A/B/C와 권장값을 함께 준다.
5. 답이 오면 `읽기 5`(`ANSWERS`)에 적는다.
6. 답을 값으로 바꿔 `읽기 6`(`PROJECT` + `MACHINE`)을 채운다. 선택지 기호가 아니라 **실제 값**으로 적는다.
7. `specs/00_DECISION_LOG.md`에 결정을 추가한다.
8. `PROJECT_MEMORY.md` 1번·3번(STEP 1이면 4번도)을 갱신한다.
9. 이 결정을 물려받는 뒤 STEP 문서의 `inherited` 값과 물려받은 결정 표를 갱신한다.
10. `python scripts/validate_specs.py --step N`을 실행한다.
11. **`읽기 7`을 그대로 읽어 준다.**

한 번에 질문을 쏟아붓지 않는다. 답하기 어려워하면 예시를 하나 보여 준다.

## 7. 결정 ID 규칙

```text
좋음   D-도시수   TASK-명소수집   TEST-정보량
나쁨   D-008      TASK-01         TEST-01
```

- 이름만 보고 무엇인지 알 수 있게 짓는다. 숫자만으로 된 ID를 새로 만들지 않는다.
- 작업은 반드시 `loop` 값(`A` 또는 `B`)을 가진다.
- 테스트는 **루프마다** 하나씩만 있다 (`TEST-정보량`, `TEST-페이지`).
- 문서 안에서는 항상 백틱으로 감싼다.

---

## 8. 결정 상속과 문서 갱신

- 앞 STEP의 결정은 뒤 STEP의 **"앞에서 물려받은 결정"** 표와 `inherited` 블록에 실제 값으로 채운다.
- **`읽기 4`(`FIXED`)는 절대 수정하지 않는다.** 질문 문장을 지우거나 바꾸지 않는다.
- 갱신은 `PROJECT` 영역 안에서만 한다.

---

## 9. 승인된 결정을 덮어쓰지 않는다

1. 이전 값 / 새 값 / 이유 / 시각 / 영향받는 STEP을 `specs/00_DECISION_LOG.md`에 기록한다.
2. 영향받는 STEP 문서의 상태를 `NEEDS_REVIEW`로 바꾼다.
3. 사람에게 영향 범위를 표로 보여 주고 확인을 받는다.
4. 같은 내용을 `PROJECT_MEMORY.md` 5번(바꾼 결정)과 3번 값에도 반영한다.

## 10. AORR 실행 규칙

```text
Act      첫 바퀴: 그 루프의 작업 목록을 순서대로 한 번씩 · 다음 바퀴부터: 부족으로 지적된 칸의 작업만
Observe  그 루프의 검사기를 한 번 실행하고 종료 코드를 읽는다
Reason   실패 원인을 하나로 좁히고 유형을 정한다
Repeat   최소 수정 → 그 루프의 검사기 → 최종 검증 명령
```

- 판정기는 그 루프의 결과물 전체를 한 번에 본다. 그래서 작업 하나마다 판정하지 않는다.
- 실패 증거 없이 수정하지 않는다.
- 원인을 여러 개 추측해 동시에 고치지 않는다.
- `RESEARCH`일 때는 **부족한 칸만** 다시 모은다. 전부 다시 하지 않는다. **지적되지 않은 칸은 손대지 않는다.**

## 11. 종료 코드가 최종 판정자다

```text
Claude "다 됐습니다"  →  근거 아님
검사기 exit 0         →  근거임

exit 0  PASS    기준을 다 채움
exit 1  ERROR   파일·명세가 깨짐 — 사람에게 넘긴다
exit 2  SHORT   아직 덜 됨 — 루프가 더 돈다
```

`1`과 `2`를 구분해서 보고한다. `2`는 정상적인 진행 중 상태다.

## 12. 되물음 (Reverse Question)

루프가 끝날 때와 상한에 걸릴 때 **혼자 판단하지 않고 물어본다.**

```text
[되물음] (어느 루프)가 끝났습니다 / 상한에 걸렸습니다.
  채운 것    : N / M 칸
  못 채운 것 : (목록과 이유)
  고르세요
   [1] 부족한 칸만 다시 모은다        (예상 시간)
   [2] 부족한 채로 다음으로 넘어간다   ← 같은 오류가 반복되면 이쪽을 권한다
   [3] 여기서 멈춘다
```

- **선택지 없이 "도와주세요"라고 쓰지 않는다.**
- 못 채운 칸 없이 통과했으면 `[2]` 는 "다음 루프로 넘어간다 ← 권장"이다 (`templates/REVERSE_QUESTION.md` 의 '통과했을 때' 양식).
  `HALT_*` 안내는 부족이 남았을 때만 붙인다.
- 못 채운 칸을 숨기지 않는다. 넘어가더라도 보고서에 그대로 적는다.
- 답은 `PROJECT_MEMORY.md`의 **7. 되물음에서 내가 고른 답**에 남긴다.
  루프 중에는 `specs/**`가 `--lock`으로 잠겨 있으므로 결정 장부에 쓰지 않는다 (쓰면 준비도 검사가 `ERROR`).

## 13. 수정 허용 범위

STEP 4에서 확정하기 전까지의 기본값이다.

**수정 금지 (보호)**

```text
specs/**   scripts/**   templates/**   CLAUDE.md   MASTER_SPEC.md   LOOP_CONTRACT.md
```

**수정 가능**

```text
USER_REQUEST.md   PROJECT_MEMORY.md   src/**   output/**   state/**   evidence/runs/**
```

보호 파일을 고쳐야 한다고 판단되면 **고치지 말고 사람에게 넘긴다.**

## 14. Evidence 기록 규칙

매 반복마다 `evidence/runs/<run_id>/`에 남긴다.

```text
실행한 명령 / 종료 코드 / 어느 루프 / 실패 유형
오류 지문 / 바꾼 파일 / 고른 다음 행동 / 로그 경로
```

남기지 않는 것:

```text
API 키, 토큰, 개인정보, 모델의 비공개 사고 과정 전체
```

## 15. 재시도 · 중단 · 사람 호출

STEP 6~7에서 확정하기 전까지의 기본값이다.

| 상황 | 행동 |
| --- | --- |
| 루프 A 반복 | 최대 3바퀴 → 되물음 |
| 루프 B 반복 | 최대 3바퀴 → 되물음 |
| 루프 C 반복 | **정확히 3회. 줄이지도 늘리지도 않는다** |
| 정성 수정이 루프 A·B를 깨뜨림 | 그 회차 수정을 되돌린다 |
| 같은 오류 지문 2회 반복 | 되물음 (넘어가기를 권한다) |
| 권한 · 환경 · 명세 충돌 | 자동 수정 금지, 즉시 사람 호출 |
| 보호 파일 변경 감지 | 즉시 중단 |
| 최종 검증 명령 통과 | 성공 종료 |

무한 재시도는 설계하지 않는다.

## 16. 정보를 모을 때

- 출처 등급을 따지지 않는다. **블로그·카페도 내용이 풍부하면 쓴다.**
- 다만 `다건` 항목은 **서로 다른 출처 2곳 이상**에서 와야 한다.
  '서로 다른'을 무엇으로 세는지는 계약의 `count_contract.distinct_source_mode` 에 있다
  (`url` 이면 주소가 다르면 다른 곳, `host` 면 도메인이 달라야 다른 곳).
- 근거·상세·취향 설명의 **최소 글자 수는 `MASTER_SPEC.md`의 `count_contract.min_chars`에 있다.**
  기준선에 맞춰 끊지 않는다. 내 말로 정리해 적고, 원문을 통째로 붙여넣지 않는다.
- **같은 문장을 복사해 칸을 채우지 않는다.** 줄 수를 맞추려고 번호만 바꿔 복제하면
  `dedup` 검사에 걸린다. 쓸 말이 없으면 줄 수가 아니라 **조사를 늘린다.**
- **이미지 주소를 기억으로 쓰지 않는다.** 반드시 조회로 얻고, 실제로 열어 본 뒤
  `image.verified`에 `status` · `content_type` · `checked_at`을 적는다.
  `banned_url_substrings`(`upload.wikimedia.org` — thumb·원본 모두)는 조회로 얻은 주소라도 계약이 막는다.
  `recommended_form`(`Special:FilePath` 형태)을 쓴다.
- 일정은 **도시마다** 여행 일수만큼 짠다. 하루는 `HH:MM` 시간 블록으로 나눈다.

```text
루프 C      : N/3회  exit <코드>
최종 명령   : python scripts/verify_all.py  exit <코드>
채운 칸     : N / M
못 채운 칸  : (목록. 없으면 "없음")
바꾼 파일   : ...
증거 위치   : evidence/runs/<run_id>/
인계본      : output/graph/  (종료 상태와 무관하게 항상 만든다)
다음 행동   : (사람이 해야 할 일)
```

`SUCCESS`가 아니면 성공했다고 쓰지 않는다.
**못 채운 칸이 있으면 반드시 적는다.** 조용히 넘어가는 것이 가장 나쁜 실패다.
