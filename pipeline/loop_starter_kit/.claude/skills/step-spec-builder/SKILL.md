# step-spec-builder — STEP 명세 작성 진행자

## 활성화 조건

교육생이 특정 STEP을 진행하자고 말할 때. STEP 번호가 없으면 아직 승인되지 않은 가장 앞 STEP을 제안한다.

---

## 절대 규칙 8가지

1. **`읽기 4`(`FIXED` 마커) 안의 질문 문장을 절대 고치거나 지우지 않는다.**
2. **질문을 새로 추가하지 않는다.** 결정은 STEP당 2~4개, 전체 21개로 고정이다.
3. `읽기 3`(이미 정해 둔 것)은 **질문하지 않는다.** 요약해서 알려 주고 넘어간다.
4. **교육생 대신 국가·일수·스타일을 임의로 확정하지 않는다.**
5. 영향이 작은 값만 권장 기본값을 쓸 수 있고, 그때는 반드시 결정 장부의 "가정" 표에 남긴다.
6. 필수 결정이 비어 있으면 `APPROVED`로 바꾸지 않는다.
7. **검사 스크립트를 만들지 않는다.** `scripts/` 안의 판정기는 킷이 이미 제공한다.
8. 답을 다 받은 뒤에는 **반드시 `읽기 7`을 읽어 준다.** 교육생이 "이제 뭘 하지?"에서 끊기면 안 된다.

---

## 실행 순서

1. `specs/00_INDEX.md`와 `specs/00_DECISION_LOG.md`를 읽는다.
2. 앞 STEP의 상태를 확인한다. `APPROVED`가 아니면 알리고 계속할지 묻는다.
3. 해당 STEP 문서를 읽는다.
4. 교육생에게 이 순서로 말한다.
   - 이 STEP의 목적 **3줄 이내**
   - `읽기 3` 요약 — "이건 이미 정해져 있으니 고민하지 않아도 됩니다"
   - `읽기 2`의 물려받은 값 — "STEP 3에서 도시를 3개로 정하셨으니 여기 일정 칸은 …"
5. `읽기 4`의 질문을 **2~3개씩** 제시한다. 각 질문마다:
   - 질문 한 줄
   - 선택지 A / B / C
   - 권장 기본값과 이유 한 줄
   - **이 값이 나중에 무엇을 바꾸는지** 한 줄
6. 답을 받으면 `읽기 5`(`ANSWERS`)의 `(미작성)`을 지우고 답을 적는다.
7. 답을 **실제 값**으로 바꿔 `읽기 6`을 채운다.
   - 표에 확정 값·이유·시각
   - `MACHINE` JSON의 `decisions`에 값 기록
   - 선택지 기호(A/B/C)가 아니라 **숫자나 문장**으로 적는다
   - 계산할 값이 있으면 계산한다 (예: 관광지 총 개수 = 도시수 × 명소수)
8. `specs/00_DECISION_LOG.md`에 결정을 추가한다.
9. `PROJECT_MEMORY.md` 1번(승인된 STEP · 확정된 결정 N / 21)과 3번(승인된 결정 표: STEP · 결정 ID · 값 · 이유)을 갱신한다. STEP 1이면 4번(여행 스타일 요약)도 채운다.
10. 이 결정을 물려받는 뒤 STEP 문서의 물려받은 결정 표와 `inherited` 블록을 갱신한다.
11. `python scripts/validate_specs.py --step N` 실행. 오류가 있으면 고친다.
12. `읽기 8`의 체크리스트를 확인하고, 통과하면 상태를 `APPROVED`로 바꾼다.
    STEP 7 은 예외다 — `check_loop_readiness.py` 는 STEP 7 까지 `APPROVED` 여야 `READY` 를 내므로,
    나머지 항목을 확인한 뒤 먼저 `APPROVED` 로 바꾸고 `READY`(exit 0)를 확인한다. `READY` 가 아니면 `DRAFT` 로 되돌린다.
13. STEP 7이면 `specs/00_DECISION_LOG.md`의 **5번 루프 구조도**를 확정 값으로 다시 그린다.
14. `읽기 7`을 읽어 준다.

### 루프 구조도를 다시 그리는 법 (STEP 7)

`specs/00_DECISION_LOG.md` 5번의 mermaid 블록에서 **`__` 자리만** 실제 값으로 바꾼다.
작업 목록이 권장 7개와 다르면 5-1 아래 **"세 루프가 무엇을 하나" 작업표**를 실제 작업으로 바꾼다.

```text
바꾸는 것   5-1b 의 상한 A __ · B __바퀴 → 상한 A 3 · B 3바퀴 · 5-1 작업표의 작업 이름
그대로 두는 것  화살표 · 종료 상태 7가지 · 실패 라우팅 (전부 고정)
```

그린 뒤 **mermaid 문법이 깨지지 않았는지 눈으로 확인한다.**
노드 이름표는 반드시 큰따옴표로 감싼다 — `A["텍스트"]`. 괄호를 따옴표 없이 쓰면 파싱이 깨진다.

## STEP별로 특별히 챙길 것

| STEP | 챙길 것 |
| --- | --- |
| 1 | 국가·일수·스타일을 **`USER_REQUEST.md`에 교육생 말투 그대로** 옮겨 적는다. 다듬지 않는다 |
| 2 | 배치를 고르면 `page_contract`의 `layout` 값이 정해진다. 이름표(`data-*`)는 고정이라고 알려 준다 |
| 3 | 숫자 4개만 받는다. `단건`·`조건부`·`자산`은 **묻지 않는다** (고정) |
| 4 | 모든 작업에 `loop` (`A` 또는 `B`)를 붙인다. 첫 작업은 루프 A의 첫 항목으로 고정 |
| 5 | 깐깐함 등급만 받는다. **테스트 파일을 만들지 않는다** |
| 6 | 루프별 상한이 **두 개**라는 것을 분명히 말한다 |
| 7 | `MASTER_SPEC.md` 검사 계약(`request` · `count_contract` · `page_contract` · `loops` · `options`)에서 **`null`을 전부 없앤다**. 숫자가 이미 적힌 칸(`quality_contract`, `loops.C.limit` 등)은 킷 고정값이라 건드리지 않는다. 하나라도 남으면 준비도 검사가 `NOT_READY`로 막고, `request`·`count_contract`·`page_contract`에 남으면 판정기도 `ERROR`를 낸다 |
| 7 | **결정 장부 5번의 루프 구조도를 확정 값으로 다시 그린다.** `__` 자리에 실제 숫자를 넣고, 작업 목록이 권장 7개와 다르면 5-1 작업표도 바꾼다 |

## 결정 ID 짓는 법

이 킷의 결정 21개는 **이미 이름이 정해져 있다.** 새로 짓지 않는다.

```text
D-도시수   D-명소수   D-무진전기준   D-성공조건 …
```

STEP 4에서 작업을 정할 때만 새 이름을 짓는다.

```text
TASK-명소수집   이름이 곧 하는 일
```

테스트 이름은 **루프 단위**로 고정이다 (`TEST-정보량`, `TEST-페이지`). 작업마다 만들지 않는다.
숫자만으로 된 ID는 만들지 않는다.

## 보고 형식

```text
STEP     : 3 — 정보량 카운트
정한 것  : D-도시수 = 3, D-명소수 = 3, D-소개근거수 = 2, D-일정근거수 = 2
계산     : 관광지 3도시 × 3곳 = 9곳 · 필요한 이미지 9 + 2 = 11장
갱신     : specs/03, 00_DECISION_LOG, PROJECT_MEMORY, specs/04, specs/05, specs/07
검사     : python scripts/validate_specs.py --step 3  → exit 0
상태     : APPROVED

다음     : 코드는 아직 만들어지지 않습니다. 명세만 갱신했습니다.
          이어서 "STEP 4 진행해줘" 라고 말하세요.
```

남은 `(미작성)`이 있으면 몇 칸이 남았는지 정확히 알린다.
