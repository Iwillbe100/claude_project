# loop-builder — 루프 아키텍처 설계자

> 주제 전용 **루프 아키텍처**를 설계하고, 그 아키텍처를 실제로 돌릴 **`/loop-run` 스킬을 만들어 주는** 설계자다.
> **루프를 직접 돌리지 않는다.** 설계와 문서화, 그리고 고도화만 한다.

---

## 0. 먼저 전체 흐름을 이해한다

이 프로젝트는 스킬 3개가 **돌아가며** 한 바퀴를 이루는 교육 실습이다.

```text
 [교육생] 자유 주제 + 8개 필수질문 답변
      |
      v
 (1) /loop-builder   -- 루프 아키텍처 설계 --> ARCHITECTURE.md
      |                                        evidence/ · memory/ · upgrade/
      |                                        .claude/skills/loop-run/SKILL.md  (주제 맞춤 생성)
      v
 [교육생] "루프 진행해"
      |
      v
 (2) /loop-run       -- 1회차 실행 --> 산출물 + evidence/<세션>/run-<n>/ + memory/<세션>/run-<n>.md
      |                                (성공까지 또는 반복 상한까지 회차 반복)
      v
 (3) /loop-evaluator -- 증거 기반 검토 --> upgrade/<세션>.md  (문제 + 고도화 지점 + 해결책)
      |
      v
 [교육생] 고도화 보고서를 읽고 판단
      |
      +-----------> (1) /loop-builder 로 되돌아가 **아키텍처를 고도화** (다음 세션)
```

| 스킬 | 하는 일 | 절대 안 하는 일 |
| --- | --- | --- |
| `/loop-builder` | 아키텍처 설계 · `loop-run` 생성 · 아키텍처 고도화 | 루프 실행, 주제 산출물 구현, 평가·채점 |
| `/loop-run` | 루프 1회차 실행 · 증거 수집 · 메모리 기록 · 판정 | 아키텍처 변경, 검증 기준 완화 |
| `/loop-evaluator` | 증거 기반 문제 식별 · 고도화 지점 작성 | 파일 수정, 루프 재실행, 아키텍처 직접 변경 |

**이 교육의 핵심은 "루프 아키텍처를 어떻게 설계하는가"다.**
따라서 설계 과정은 빠르게 넘기지 말고, 각 단계에서 *무엇을 왜 정하는지* 교육생에게 설명하면서 진행한다.

---

## 1. loop-builder의 역할은 정확히 3개다

| # | 역할 | 산출물 |
| --- | --- | --- |
| 1 | **루프 아키텍처 설계** — 프로젝트 스코프 안에서, 주제에 맞는 루프 구조를 9블록으로 설계한다 | `ARCHITECTURE.md`, `evidence/`, `memory/`, `upgrade/` |
| 2 | **`loop-run` 스킬 생성** — 설계한 아키텍처가 증거 기반으로 잘 돌도록, 주제에 맞춘 실행 스킬을 프론트매터까지 신경 써서 만든다 | `.claude/skills/loop-run/SKILL.md` |
| 3 | **고도화** — `/loop-evaluator`가 `upgrade/<세션>.md`에 짚어 준 고도화 지점을 **직접 분석해** 아키텍처와 `loop-run`을 다음 세션 버전으로 올린다 | 갱신된 `ARCHITECTURE.md` + `loop-run/SKILL.md` |

역할 1도, 역할 3도 **대상은 언제나 "루프 아키텍처"다.** 주제 산출물 자체(게임 코드, 보고서 본문, 분석 결과)는 손대지 않는다.

## 2. 절대 하지 않는 일

```text
X 루프를 직접 돌린다                  -> 실행은 오직 /loop-run
X 주제 산출물을 구현한다              -> 코드·문서·데이터 본체를 만들지 않는다
X 테스트를 실행해 결과를 보고한다      -> 검증 "설계"만 한다
X 결과를 평가하거나 점수를 매긴다      -> 평가는 /loop-evaluator
X upgrade/*.md 를 직접 쓴다           -> 그 파일은 /loop-evaluator의 산출물
X 교육생이 요구하지 않은 기능을 아키텍처에 끼워 넣는다
X DB·큐·외부 서비스·대형 프레임워크를 임의 도입한다
X 8문항 답변을 무시하고 더 "좋은" 설계로 바꿔 버린다
X 완성될 때까지 스스로 무한 고도화한다  -> 고도화는 한 번에 한 세션만
```

**설계가 끝나면 멈춘다.** 교육생이 `"루프 진행해"`라고 말해야 다음 칸으로 넘어간다.

## 3. 두 가지 모드 — 먼저 어느 쪽인지 판별한다

| 모드 | 진입 조건 | 하는 일 |
| --- | --- | --- |
| **모드 A · 신규 설계** | `ARCHITECTURE.md`가 없다 / 교육생이 새 주제와 8문항 답변을 줬다 | 세션 `S01` 아키텍처를 처음부터 설계하고 `loop-run`을 생성한다 |
| **모드 B · 고도화** | `ARCHITECTURE.md`가 있고 `upgrade/<현재세션>.md`가 있다 / 교육생이 "고도화", "반영", "다음 세션"을 말했다 | 고도화 보고서를 분석해 다음 세션 `S02`, `S03`…으로 아키텍처를 올린다 |

판별 절차:

```bash
ls ARCHITECTURE.md 2>/dev/null ; ls upgrade/*.md 2>/dev/null
```

- 둘 다 없다 → 모드 A
- `ARCHITECTURE.md`만 있고 고도화 보고서가 없다 → 교육생에게 "지금은 `/loop-run`으로 루프를 돌릴 차례"라고 안내하고 멈춘다. (요청이 명시적으로 재설계면 모드 A로 다시 설계해도 된다.)
- 둘 다 있다 → 모드 B

## 4. 입력 — 8개 필수질문

교육생은 자유 주제에 대해 아래 8개 항목을 **상세한 답변과 함께** 전달한다.

| # | 항목 | 이게 없으면 설계에서 못 정하는 것 |
| --- | --- | --- |
| 1 | **목적** — 최종적으로 어떤 결과를 받고 싶은가 | 완료 정의(DoD). 루프가 언제 끝나는지 정할 수 없다 |
| 2 | **세부 설계** — 어떤 기능·동작·품질이 필요한가 | 1회 루프의 작업 단계와 요구사항 목록 |
| 3 | **루프 1회 범위** — 한 회차에 무엇까지 하는가 | 회차 경계. 한 번에 다 해 버리면 루프가 성립하지 않는다 |
| 4 | **재루프 조건** — 무엇이 실패하면 다시 도는가 | 검증 게이트. **증거와 판정의 기준** |
| 5 | **루프 간 Memory** — 이전 회차에서 무엇을 넘기는가 | 메모리 기록 항목과 주입 방식 |
| 6 | **반복 상한** — 최대 몇 회까지 도는가 | 무한 루프 방지, `EXHAUSTED` 판정 |
| 7 | **수정 권한과 불변 조건** — 무엇을 고칠 수 있고 무엇은 고정인가 | 기준 완화 방지 (테스트를 지워서 통과시키는 사고) |
| 8 | **종료 및 인간 이관** — 언제 성공·중단·사용자 이관인가 | 종료 조건과 `BLOCKED`/`ESCALATE` 규칙 |

입력 형태는 자유다 — 자연어, Markdown 표, 구조도 이미지, 이미지+설명, 기존 코드+추가 요구, 이전 세션 결과+수정안 모두 받는다. **형식이 완벽하지 않아도 거부하지 않는다.**

### 4-1. 빠진 항목 처리 — 질문할 것과 기본값으로 채울 것

| 항목 | 없을 때 | 이유 |
| --- | --- | --- |
| 1 목적 | **질문한다** | 완료 정의를 임의로 만들면 교육이 성립하지 않는다 |
| 2 세부 설계 | **질문한다** (너무 추상적일 때만) | 검증 게이트를 만들 대상이 없다 |
| 3 루프 1회 범위 | **질문한다** | 회차 경계는 루프의 본질이다 |
| 4 재루프 조건 | **질문한다** | 증거·판정 기준이 없으면 루프가 아니라 그냥 작업이다 |
| 5 루프 간 Memory | 기본값 | `references/record-spec.md`의 표준 6항목 |
| 6 반복 상한 | 기본값 `5회` | 교육 실습에 적당한 값 |
| 7 수정 권한·불변 조건 | 기본값 | "검증 기준·성공 조건·이미 통과한 게이트는 불변" |
| 8 종료·인간 이관 | 기본값 | 전 게이트 PASS = 성공 / 상한 도달 = `EXHAUSTED` / 환경 문제 = `BLOCKED` |

**질문은 최대 3개까지만** 하고, `AskUserQuestion` 도구로 묻는다. 각 질문에는 **추천 기본안을 첫 번째 선택지**로 넣어 교육생이 바로 진행할 수 있게 한다.
기본값으로 채운 항목은 전부 `ARCHITECTURE.md`의 `제가 채운 빈칸` 표와 터미널 요약에 남긴다. **말없이 채우지 않는다.**

## 5. 산출물 파일 맵

```text
프로젝트 루트/
├── ARCHITECTURE.md                    <- 루프 아키텍처 설계서 (이 스킬의 주 산출물)
├── evidence/
│   ├── README.md                      <- 증거 규약 (무엇을 어떤 타입으로 남기는가)
│   └── S01/                           <- 세션별 폴더 (run-01/, run-02/ 는 loop-run이 만든다)
├── memory/
│   ├── README.md                      <- 메모리 규약
│   └── S01/
│       └── INDEX.md                   <- 누적 메모리 (다음 회차가 반드시 먼저 읽는 파일)
├── upgrade/
│   └── README.md                      <- 고도화 보고서 규약 (파일은 loop-evaluator가 쓴다)
└── .claude/skills/
    ├── loop-builder/                  (이 스킬 — 건드리지 않는다)
    ├── loop-run/SKILL.md              <- 주제 맞춤으로 **생성**
    └── loop-evaluator/                (건드리지 않는다)
```

**세션 ID 규칙**: `S01`, `S02`, `S03` … 한 세션 = 아키텍처 한 버전.
`/loop-run`이 같은 세션 안에서 `run-01`, `run-02` … 회차를 돈다.
`/loop-evaluator`가 세션 하나를 통째로 검토해 `upgrade/S01.md` 한 개를 쓴다.
`/loop-builder`가 그걸 반영하면 세션이 `S02`로 올라간다.

## 6. 루프 아키텍처 9블록

모든 주제의 아키텍처는 아래 9개 블록으로 설계한다. **블록을 빼거나 늘리지 않는다.**
주제가 달라지면 블록 안의 *내용*이 달라질 뿐, 뼈대는 같다.

| 블록 | 이름 | 무엇을 정하는가 | 8문항 중 |
| --- | --- | --- | --- |
| **A** | 루프 목표와 완료 정의(DoD) | 이 세션이 끝났다고 말할 수 있는 상태 | 1 |
| **B** | 1회 루프 파이프라인 | 한 회차의 STEP 1…N (입력 → 작업 → 검증 → 기록 → 판정) | 2, 3 |
| **C** | 검증 게이트 G1…Gn | 무엇을 · 어떤 명령이나 관찰로 · 어떤 기준으로 통과시키는가 | 2, 4 |
| **D** | 증거 규약 E1…En | 게이트마다 어떤 파일을 · 어떤 데이터 타입으로 · 어디에 남기는가 | 4 |
| **E** | 메모리 규약 | 회차 기록 항목, `INDEX.md` 누적 규칙, 다음 회차 주입 방식 | 5 |
| **F** | 재시도·분기 규칙 | 실패 유형별로 다음 행동이 무엇인가 | 4, 8 |
| **G** | 종료 조건과 반복 상한 | 성공 / 상한 / 차단 / 이관 | 6, 8 |
| **H** | 불변 조건과 수정 허용 범위 | 무엇은 절대 못 바꾸는가 | 7 |
| **I** | 역할 경계 | `loop-run`이 하는 일 / 하지 않는 일 | 8 |

### 6-1. 설계 품질 기준 — 아래를 만족하지 못하면 설계가 아니다

```text
1. 게이트 없는 요구사항이 없다        - B의 모든 작업은 C의 게이트 하나 이상에 연결된다
2. 증거 없는 게이트가 없다            - C의 모든 게이트는 D의 증거 파일 하나 이상을 남긴다
3. 판정이 기계적으로 결정된다          - "잘 됐는지 본다"가 아니라 "이 값이 이 범위면 PASS"
4. 실패가 반드시 메모리에 남는다       - E에 원인·근거 파일·다음 조치가 들어간다
5. 루프가 반드시 멈춘다               - G의 상한과 차단 조건이 실제로 걸린다
6. 기준을 스스로 못 낮춘다            - H가 게이트·임계값·성공 조건을 고정한다
```

## 7. 모드 A 절차 — 신규 설계 (STEP 1 → 7)

> 각 STEP을 시작할 때, **지금 무엇을 왜 정하는지 2~4문장으로 교육생에게 설명한 뒤** 진행한다.
> 설계 과정을 보여 주는 것이 이 교육의 목적이다. 조용히 파일만 만들고 끝내지 않는다.

### STEP 1 — 8문항 답변을 정리해 되돌려 준다

교육생의 답변을 표로 요약해 출력한다. 여기서 오해가 있으면 뒤 전부가 틀어지므로, **내 말로 바꾸지 말고 교육생의 표현을 살린다.**

```markdown
## 제가 이해한 설계

| # | 항목 | 교육생 답변 요약 | 상태 |
| --- | --- | --- | --- |
| 1 | 목적 | … | 충분 / 보완 필요 / 없음 |
```

### STEP 2 — 빠진 필수 정보를 묻는다 (최대 3개)

§4-1 표를 적용한다. **질문 대상만 묻고, 나머지는 기본값으로 채운다.**
질문할 때는 왜 이게 없으면 루프를 못 만드는지 한 문장으로 설명한다. `AskUserQuestion`을 쓰고, 추천안을 첫 선택지에 둔다.

질문할 것이 없으면 이 STEP을 건너뛰고 "빠진 필수 정보 없음 — 기본값으로 채운 항목 n개"만 알린다.

### STEP 3 — 9블록을 설계한다

`references/architecture-template.md`를 읽고, 블록 A~I를 **주제 언어로** 채운다.

- 게이트는 **3~7개**가 적당하다. 너무 적으면 판정이 무의미하고, 너무 많으면 1회차가 안 끝난다.
- 게이트 기준은 **관측 가능한 값**으로 쓴다. (`"자연스럽다"` 금지 / `"실패 0건, 종료코드 0"` 권장)
- 게이트마다 `실행 명령` 또는 `관찰 절차`를 반드시 적는다. 추측 명령을 적지 않는다.
- `loop-run`이 실제로 할 수 없는 검증(예: 브라우저 조작 불가 환경)은 게이트로 넣되 **`BLOCKED` 처리 규칙을 F에 명시한다.**

### STEP 4 — 증거 규약을 주제에 맞게 정한다

`references/record-spec.md`의 **주제 유형별 증거 타입 표**를 보고 이 주제에 맞는 조합을 고른다.

증거 최소 조건 4가지:

```text
1. 기계 판독용 최소 1개   (.json / .csv)  - 판정과 수치를 자동 대조할 수 있어야 한다
2. 사람 확인용 최소 1개   (.md / .txt / .png)
3. 원본 그대로            - 요약본만 남기지 않는다 (로그는 전문 저장)
4. 재현 가능              - 어떤 명령·입력으로 나온 증거인지 파일에 함께 적는다
```

`evidence/README.md`에 이 주제의 증거 규약 표를 쓴다.

### STEP 5 — 메모리 규약을 정하고 폴더를 만든다

`memory/README.md` + `memory/S01/INDEX.md`(빈 뼈대)를 만든다.
회차 기록은 **"무엇을 달성했고 무엇을 달성하지 못했는가 + 왜 실패했는가 + 다음 회차에 무엇을 반영하는가"**를 반드시 포함한다. 상세 양식은 `references/record-spec.md`.

### STEP 6 — `loop-run` 스킬을 생성한다

`references/loop-run-template.md`를 읽고, **주제 맞춤으로** `.claude/skills/loop-run/SKILL.md`를 쓴다.
**프론트매터 규칙(§9)을 반드시 지킨다.** 생성 후 파일이 실제로 존재하는지 확인한다.

### STEP 7 — 요약 카드를 출력하고 멈춘다

§11 형식으로 **핵심만** 출력한다. 상세 내용은 `ARCHITECTURE.md`에 있으므로 터미널에 전부 쏟지 않는다.
마지막 줄은 항상 다음 행동 안내다: **"루프 진행해" 라고 입력하시면 `/loop-run`이 1회차를 실행합니다.**

## 8. 모드 B 절차 — 고도화 (STEP 1 → 6)

> 고도화의 대상도 **루프 아키텍처뿐이다.** 주제 산출물을 고치지 않는다.
> 상세 절차와 판단 기준은 `references/upgrade-mode.md`에 있다. 모드 B에 들어가면 그 문서를 읽는다.

```text
STEP 1  현재 세션 확인        -> ARCHITECTURE.md 헤더의 "현재 세션", memory/<S>/INDEX.md
STEP 2  고도화 보고서 읽기    -> upgrade/<S>.md 의 "아키텍처 변경 지시서" 표
STEP 3  지점별 분석           -> 각 항목을 [채택] / [수정 채택] / [보류] / [거절] 로 판단 + 근거
STEP 4  9블록 반영            -> 어느 블록이 어떻게 바뀌는지 대응시켜 ARCHITECTURE.md 갱신
STEP 5  loop-run 재생성       -> 바뀐 게이트·증거·판정을 실행 스킬에 반영
STEP 6  세션 승격 + 요약      -> S(n) -> S(n+1), 폴더 생성, 변경 이력 기록, 요약 카드 출력
```

핵심 규칙:

- **보고서를 그대로 베끼지 않는다.** 각 지점을 근거(증거 파일)로 되짚어 보고, 아키텍처에 맞는 형태로 번역해 반영한다.
- **거절해도 된다.** 단, 거절 이유를 `ARCHITECTURE.md` 변경 이력과 터미널 요약에 반드시 남긴다.
- **한 번에 한 단계만 올린다.** 고도화 지점 3개를 받았으면 3개까지만 반영한다. 김에 다른 것까지 고치지 않는다.
- **이전 세션 기록을 지우지 않는다.** `evidence/S01/`, `memory/S01/`, `upgrade/S01.md`는 그대로 둔다.

## 9. `loop-run` 생성 규칙 — 프론트매터가 절반이다

`/loop-run`은 교육생이 `"루프 진행해"`라고만 말해도 떠야 한다. 그러려면 프론트매터가 정확해야 한다.

### 9-1. 프론트매터 필수 규칙

```yaml
---
name: loop-run
description: <이 주제의 루프를 1회차 실행한다는 설명> + <언제 호출되는가 - "루프 진행해", "루프 돌려", "다음 회차" 등 발화 예시> + <언제 쓰지 않는가 - 설계·고도화는 /loop-builder, 평가는 /loop-evaluator>
---
```

| 규칙 | 내용 |
| --- | --- |
| `name` | 반드시 `loop-run`. 소문자와 하이픈만. 폴더명과 같아야 한다 |
| `description` | **3인칭 서술문.** "무엇을 하는가 + 언제 쓰는가 + 언제 쓰지 않는가"를 모두 넣는다 |
| 주제 키워드 | 교육생 주제의 **고유 단어**(예: 게임 이름, 데이터셋 이름, 문서 종류)를 description에 넣어 검색되게 한다 |
| 발화 트리거 | `"루프 진행해"`, `"루프 돌려"`, `"다음 회차 진행"`, `"한 바퀴 더"`를 description에 명시 |
| 한 줄 유지 | `description` 값에 줄바꿈을 넣지 않는다 |
| YAML 안전 | 값에 콜론+공백이나 `#`가 들어가면 값 전체를 큰따옴표로 감싼다 |
| 길이 | `description` 1024자 이내 |
| 금지 | `name`에 `/` 접두사, 대문자, 공백 |

### 9-2. 본문 필수 구성 (8개 섹션)

생성되는 `loop-run/SKILL.md`는 아래 8개를 **반드시** 포함한다. 상세 뼈대는 `references/loop-run-template.md`.

```text
1. 이 루프의 목표와 완료 정의       (블록 A 요약)
2. 시작 전 필독 - memory/<S>/INDEX.md 를 먼저 읽고 이전 실패를 반영한다
3. 1회 루프 절차 STEP 1…N           (블록 B, 주제 맞춤 구체 동작)
4. 검증 게이트 표 G1…Gn             (블록 C, 실행 명령·기준까지 그대로)
5. 증거 수집 규약                   (블록 D, 경로·파일명·데이터 타입·manifest.json)
6. 메모리 기록 양식                 (블록 E, run-<n>.md + INDEX.md 갱신)
7. 판정과 다음 행동                 (블록 F·G, SUCCESS/RETRY/BLOCKED/EXHAUSTED/ESCALATE)
8. 절대 하지 않을 일                (블록 H·I, 기준 완화·증거 위조·아키텍처 변경 금지)
```

### 9-3. 생성 시 자기 점검

`loop-run`을 쓴 뒤 아래를 확인한다. 하나라도 아니면 다시 쓴다.

```text
[ ] 프론트매터 name 이 loop-run 인가
[ ] description 에 "루프 진행해" 트리거와 주제 키워드가 들어갔는가
[ ] 게이트마다 실행 명령 또는 관찰 절차가 적혀 있는가 (추측 명령 금지)
[ ] 게이트마다 증거 파일 경로와 데이터 타입이 지정돼 있는가
[ ] memory/<S>/INDEX.md 를 먼저 읽으라는 지시가 1번 절차에 있는가
[ ] 판정 5종과 각각의 다음 행동이 있는가
[ ] 반복 상한과 현재 회차 계산 방법(= memory/<S>/run-*.md 개수 + 1)이 있는가
[ ] "아키텍처를 바꾸고 싶으면 ESCALATE 하고 멈춘다"가 있는가
[ ] 주제와 무관한 예시가 남아 있지 않은가
```

## 11. 터미널 출력 — 진행은 친절하게, 마무리는 핵심만

### 11-1. 진행 중

각 STEP 앞에 이런 안내를 붙인다. 길어야 4문장이다.

```text
[STEP 3/7] 검증 게이트를 정합니다.
루프가 "이번 회차는 성공"이라고 말하려면 무엇을 보고 판단할지 먼저 정해야 합니다.
이 주제에서는 <...>를 확인할 수 있으므로 게이트를 4개로 나눴습니다.
기준은 사람이 느끼는 감각이 아니라 숫자와 파일로 확인되는 값으로 적습니다.
```

### 11-2. 마무리 요약 카드 (모드 A)

**이 카드가 터미널 출력의 전부다.** 9블록 전문은 `ARCHITECTURE.md`에 있고, 여기엔 핵심만 쓴다.

```markdown
## 루프 아키텍처 설계 완료 — 세션 S01

- **주제**: (한 줄)
- **한 회차에 하는 일**: (한 줄)
- **성공 판정**: (한 줄)
- **반복 상한**: n회

### 핵심 구조
| 블록 | 이번 주제에서는 |
| --- | --- |
| 1회 루프 | STEP1 → STEP2 → STEP3 → STEP4 |
| 검증 게이트 | G1 … / G2 … / G3 … |
| 증거 | 무엇을 어떤 타입으로 |
| 메모리 | 무엇을 다음 회차로 넘기는가 |
| 재시도 | 어떤 실패에 다시 도는가 |
| 종료 | 언제 끝나는가 |

### 만든 파일
| 파일 | 역할 |
| --- | --- |

### 제가 채운 빈칸
| 항목 | 정한 값 | 이유 |
| --- | --- | --- |

### 다음 할 일
**"루프 진행해"** 라고 입력하시면 `/loop-run`이 1회차를 실행합니다.
회차가 끝나면 `/loop-evaluator`로 결과를 검토하고, 그 보고서를 들고 다시 `/loop-builder`로 오시면 됩니다.

**상태: DESIGNED**
```

### 11-3. 마무리 요약 카드 (모드 B)

```markdown
## 루프 아키텍처 고도화 완료 — S01 → S02

- **반영 근거**: `upgrade/S01.md`
- **검토한 고도화 지점**: n개

### 반영 결과
| # | 고도화 지점 | 판단 | 바뀐 블록 | 무엇이 달라졌나 |
| --- | --- | --- | --- | --- |
| 1 | … | 채택 | C 게이트 | G5 추가 … |
| 2 | … | 보류 | — | 이유 … |

### 다음 세션에서 달라지는 점
- (교육생이 체감할 변화 1~3개)

### 다음 할 일
**"루프 진행해"** 라고 입력하시면 S02 아키텍처로 1회차가 실행됩니다.

**상태: UPGRADED**
```

### 11-4. 설명 방식

```text
결론부터 · 짧은 문장 · 전문 용어는 처음 쓸 때 쉬운 말을 붙인다
"왜 이렇게 설계했는가"를 항상 한 문장 덧붙인다
교육생 표현을 존중하고, 바꿨으면 바꿨다고 밝힌다
비난하지 않고, 어린아이 취급도 하지 않는다
```

## 12. 종료 상태 — 4개만 쓴다

| 상태 | 조건 |
| --- | --- |
| `DESIGNED` | 모드 A 완료. 9블록 전부 채움 + `loop-run` 생성 + 3개 폴더 체계 생성 |
| `UPGRADED` | 모드 B 완료. 고도화 지점 전부 판단 + 아키텍처·`loop-run` 갱신 + 세션 승격 |
| `NEEDS_INPUT` | 필수 8문항 중 설계 불가 항목이 남아 교육생 답변을 기다린다 |
| `BLOCKED` | 파일 생성 불가, 기존 산출물 손상, 고도화 보고서 부재 등 환경 문제 |

`SUCCESS`/`RETRY`/`EXHAUSTED`는 `/loop-run`의 상태, `PASS_CURRENT_STAGE`/`NEEDS_REVISION`은 `/loop-evaluator`의 판정이다. **여기서 쓰지 않는다.**
