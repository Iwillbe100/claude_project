# loop-evaluator — 증거 기반 고도화 보고서 작성자

> 한 세션 동안 돈 루프의 **산출물과 증거를 대조해** 무엇이 실제로 됐고 무엇이 안 됐는지 가리고,
> 다음 세션에서 **루프 아키텍처를 어떻게 올릴지**를 `upgrade/<세션>.md` 한 장에 적는다.
> **점수를 매기는 스킬이 아니다. 파일을 고치는 스킬도 아니다.**

---

## 0. 이 스킬의 자리

```text
 (1) /loop-builder    루프 아키텍처 설계 / 고도화
        |                                    ^
        v                                    |
 (2) /loop-run        회차 실행 · 증거 · 메모리    |
        |                                    |
        v                                    |
 (3) /loop-evaluator  증거 기반 검토 --> upgrade/<세션>.md
        |                                    |
        +--- 교육생이 읽고 판단 --------------+
```

교육생이 **"내 루프 설계의 어디가 부족했는가"**를 스스로 깨닫게 만드는 것이 목적이다.
따라서 결론만 던지지 않는다. **무슨 일이 있었는지 → 왜 그랬는지 → 설계의 어느 빈틈 때문인지 → 어떻게 고치는지** 순으로 쓴다.

---

## 1. 핵심 산출물 — `upgrade/<세션>.md` 한 개

| 항목 | 규칙 |
| --- | --- |
| 경로 | `upgrade/S01.md`, `upgrade/S02.md` — **세션당 정확히 하나** |
| 양식 | `references/upgrade-template.md`를 **그대로** 사용. 절 순서·제목·표 구조를 바꾸지 않는다 |
| 형식 고정 이유 | 세션끼리 나란히 놓고 비교할 수 있어야 교육생이 "무엇이 나아졌는지"를 본다 |
| 근거 | 모든 문제에 **실제 파일 경로**가 붙는다. 경로 없는 지적은 쓰지 않는다 |
| 해결책 | 모든 문제에 **해결책 + 확인 방법**이 붙는다. 문제만 나열하지 않는다 |
| 덮어쓰기 | 같은 세션 보고서가 이미 있으면 덮어쓰지 않고, 교육생에게 알린 뒤 판단을 받는다 |

터미널에는 **요약만** 출력한다. 상세 내용은 파일에 있다. (§7)

## 2. 절대 규칙

```text
1. 문제는 한 번에 최대 3개.           전수 검사·엣지 케이스 나열을 하지 않는다
2. 평가 대상을 수정하지 않는다.        산출물·evidence/·memory/·ARCHITECTURE.md·loop-run 전부 읽기 전용
   (실패한 검증을 "고쳐서" 다시 돌려 보는 것도 수정이다)
3. 평가 기준을 새로 만들지 않는다.     기준은 ARCHITECTURE.md의 완료 정의와 게이트, 교육생 8문항이다
4. 확인하지 않은 것을 확인했다고 쓰지 않는다.
5. /loop-builder 나 /loop-run 을 같은 턴에 호출하지 않는다.
6. 스스로 반복하지 않는다.            한 번 평가하고 멈춘다
7. 점수·백분율·성숙도 등급을 쓰지 않는다.
8. 교육생이 요구하지 않은 개념을 필수 조건으로 강요하지 않는다. (DB·분산·프로덕션 운영 등)
9. 실습 결과를 프로덕션 기준으로 실패 처리하지 않는다.
10. 외부 서비스·유료 API 호출, git commit/push/reset 을 하지 않는다.
```

**유일한 쓰기 권한은 `upgrade/<세션>.md` 하나뿐이다.**

## 3. 워크플로

### STEP 1 — 대상 세션을 정하고 자료를 모은다

```bash
sed -n '1,20p' ARCHITECTURE.md                 # 현재 세션 · 완료 정의 · 상한
cat memory/S01/INDEX.md                        # 세션이 어떻게 끝났나
ls memory/S01/run-*.md                         # 회차 수
ls evidence/S01/*/                             # 증거 존재 여부
cat evidence/S01/run-*/manifest.json           # 게이트 판정 원본
```

| 자료 | 위치 | 없으면 |
| --- | --- | --- |
| 아키텍처 9블록 · 완료 정의 · 게이트 | `ARCHITECTURE.md` | 평가 기준이 없다 → `CANNOT_VERIFY` |
| 회차 판정과 관측값 | `evidence/<S>/run-*/manifest.json` | 증거 기반 평가 불가 → 그 자체가 문제 1번 |
| 증거 파일 | `evidence/<S>/run-*/` | 〃 |
| 회차 기록 6절 | `memory/<S>/run-*.md` | 메모리 설계 부재 → 문제로 지적 |
| 누적 메모리 | `memory/<S>/INDEX.md` | 〃 |
| 실행 스킬 | `.claude/skills/loop-run/SKILL.md` | 설계가 실행으로 옮겨졌는지 확인 불가 |
| 산출물 | `ARCHITECTURE.md` 블록 A·B가 가리키는 경로 | 결과 확인 불가 |
| 교육생 8문항 원문 | 대화, 또는 `ARCHITECTURE.md`의 설계 근거 | 원래 의도 대조 불가 |

자료가 일부만 있어도 평가한다. **다만 평가 가능한 범위를 먼저 밝힌다.**

### STEP 2 — 평가 수준을 선언한다

| 수준 | 뜻 |
| --- | --- |
| 문서 기반 | 아키텍처와 메모리만 읽었다 |
| 증거 기반 | `manifest.json`과 증거 파일을 열어 관측값을 확인했다 |
| 실행 기반 | 게이트를 **있는 그대로** 직접 한 번 실행해 재현했다 |

가능하면 증거 기반 이상으로 올린다. 증거가 없으면 "증거 부재" 자체가 가장 중요한 문제다.

### STEP 3 — 안전한 최소 재현만 한다

**해도 되는 것** (대상을 바꾸지 않고, 각 1회)

- `ARCHITECTURE.md` 게이트 표에 적힌 명령을 **그대로** 한 번 실행한다. 명령을 추측하지 않는다
- 실패 원인 확인을 위해 같은 명령을 한 번 더 실행한다
- 문법·형식만 보는 정적 확인
- 원래 요구된 관찰형 게이트가 있고 그 도구가 있으면 **짧게 한 번** 관찰한다

**하지 않는 것**

- 대상을 고쳐 놓고 다시 실행
- 새 검증을 대규모로 작성, 부하 테스트, 외부에 부작용을 남기는 실행
- 도구가 없는데 수행한 척하기 → "확인하지 못함"으로 남기고 평가 수준을 낮춘다

> `/loop-run`이 게이트를 **수행하지 않았는데 `SUCCESS`로 보고했다면, 그것 자체가 문제 1번이다.**
> 대신 수행해서 통과시켜 주는 것이 아니라, **근거가 비어 있다는 사실**을 지적한다.

### STEP 4 — 근거의 신뢰 순서를 지킨다

```text
1. 직접 재현한 실행 결과
2. evidence/ 의 원본 증거 파일 (manifest.json 의 observed 값)
3. 산출물 실물
4. memory/ 의 회차 기록
5. ARCHITECTURE.md 와 교육생 8문항
6. /loop-run 의 보고 문장          <- 가장 낮다. 그대로 믿지 않는다
```

보고 문장과 증거가 어긋나면 **증거를 따르고, 어긋났다는 사실 자체를 문제로 올린다.**

```text
loop-run 보고:  G3 PASS
manifest.json:  G3 result=PASS, observed=""     <- 관측값이 비어 있다
증거 폴더:      g3-*.png 없음
판정:           증거 없는 통과. 문제 1번으로 올린다
```

### STEP 5 — 완료 정의와 대조한다

`ARCHITECTURE.md` 블록 A의 `D1~Dn`을 한 줄씩 대조해 세 갈래로 나눈다.

| 갈래 | 뜻 | 판정에 쓰는 법 |
| --- | --- | --- |
| 이번 세션 필수 | 교육생이 직접 요구했고 완료 정의에 있다 | 미충족이면 `NEEDS_REVISION` |
| 설계자가 채운 기본값 | `ARCHITECTURE.md`의 "제가 채운 빈칸" 표 | 문제가 되면 고도화 후보로 올린다 |
| 다음 고도화 후보 | 이번 요구엔 없지만 실제로 쓰면 걸릴 것 | **빠졌다는 이유만으로 실패 처리하지 않는다** |

### STEP 6 — 현재 루프가 어떻게 돌았는지 먼저 쓴다

지적하기 전에 **5문장 이내**로 이번 세션의 흐름을 정리한다. 교육생이 전체를 먼저 이해해야 지적이 학습이 된다.

### STEP 7 — 문제를 최대 3개 고른다

우선순위:

```text
1. 증거 없이 통과로 처리된 것          (가장 위험 — 루프가 거짓말을 한 것)
2. 완료 정의를 못 채웠는데 성공처럼 끝난 것
3. 루프가 멈추지 않거나 같은 실패를 반복한 것
4. 교육생이 바로 체감할 산출물 문제
5. 다음 설계에서 간단히 개선할 수 있는 것
```

각 문제에 **확인 수준**을 붙인다: `실행으로 확인` · `증거로 확인` · `기록으로 확인` · `발생 가능성 있음` · `현재 자료로 확인 불가`.

### STEP 8 — 루프 아키텍처 9블록 관점으로 되짚는다

**전 블록을 다 평가하지 않는다.** 실제 문제가 난 블록만 본다.

| 블록 | 확인할 것 | 볼 곳 |
| --- | --- | --- |
| A 목표·완료 정의 | 게이트 통과가 실제 목적 달성과 같은가. 일부만 됐는데 SUCCESS인가 | `ARCHITECTURE.md` D표 vs `manifest.json` |
| B 1회 범위 | 한 회차가 실제로 끝났는가. 범위가 너무 커서 매번 미완인가 | `memory/<S>/run-*.md` 1·2절 |
| C 게이트 | 게이트가 완료 정의를 다 덮는가. 기준이 관측 가능한가. 실행 명령이 실제였는가 | 게이트 표 vs `manifest.json`의 `command`·`observed` |
| D 증거 | 게이트마다 증거가 있는가. 기계 판독/사람 확인이 둘 다 있는가. 원본인가 | `evidence/<S>/run-*/` 실제 파일 목록 |
| E 메모리 | 실패 원인이 구체적인가. 다음 회차가 실제로 반영했는가. 해결/미해결이 구분되는가 | `run-*.md` 3·5절, `INDEX.md` |
| F 재시도 | 고칠 수 없는 실패에 계속 RETRY하지 않았는가. 반복 실패에 ESCALATE 했는가 | `INDEX.md` 반복 실패 표 |
| G 종료·상한 | 성공 시 즉시 끝났는가. 상한이 실제로 걸렸는가. `EXHAUSTED`가 성공처럼 보고되지 않았는가 | 회차 수 vs 상한, 마지막 `verdict` |
| H 불변 | 게이트·기준·임계값이 바뀌지 않았는가. 증거를 덮어쓰지 않았는가 | `run-*.md` 4절의 변경 파일 목록 |
| I 역할 경계 | `loop-run`이 아키텍처를 건드리지 않았는가. 한 호출에 한 회차만 돌았는가 | `run-*.md` 4절, 회차 파일 수 |

### STEP 9 — 지금 고칠 것과 다음에 올릴 것을 나눈다

| 지금 고쳐야 하는 것 | 다음 단계에서 고도화할 것 |
| --- | --- |
| 완료 정의 미충족 · 증거 없는 PASS · 요구된 검증 미수행 · 실패가 메모리에 없음 · 상한이 안 걸림 · 기준이 완화됨 | 게이트 세분화 · 증거 타입 보강 · 산출물 품질 개선 · 범위 조정 · 자동화 확대 |

**다음 단계 항목 때문에 현재 단계를 실패 처리하지 않는다.**

### STEP 10 — 8문항과 9블록 양쪽으로 지목한다

발견한 문제마다 **교육생이 어디를 고쳐야 하는지** 두 좌표로 짚는다.

| 발견한 문제 | 8문항 | 9블록 |
| --- | --- | --- |
| 어떤 조건을 아무도 검사하지 않았다 | 4 재루프 조건 | C 게이트 |
| 통과 근거 파일이 없다 | 4 재루프 조건 | D 증거 |
| 같은 실패를 반복했다 | 5 루프 간 Memory | E 메모리 |
| 상한이 실제로 안 걸렸다 | 6 반복 상한 | G 종료 |
| 기준이 통과를 위해 바뀌었다 | 7 수정 권한과 불변 조건 | H 불변 |
| 한 회차에 너무 많은 걸 하려 했다 | 3 루프 1회 범위 | B 파이프라인 |
| 막혔는데 사용자에게 넘기지 않았다 | 8 종료 및 인간 이관 | F·I |

### STEP 11 — 아키텍처 변경 지시서를 쓴다

`/loop-builder`가 **그대로 집어 반영할 수 있는 형태**로 쓴다. 이 절이 다음 세션의 입력이다.

| # | 대상 블록 | 현재 상태 | 바꿀 내용 (구체적으로) | 근거 파일 | 해결됐다고 볼 기준 |
| --- | --- | --- | --- | --- | --- |

작성 규칙:

```text
O "G5를 추가한다: <대상>을 <명령>으로 검사해 <기준>이면 PASS"  - 그대로 쓸 수 있다
O 근거 파일 경로를 반드시 적는다
O 해결 확인 기준을 관측 가능한 값으로 적는다

X "게이트를 강화한다"                    - 무엇을 어떻게인지 없다
X "메모리를 개선한다"                     - 실행 불가
X "리팩터링이 필요하다"                   - 아키텍처 지시가 아니다
```

### STEP 12 — 판정은 셋 중 하나

| 판정 | 뜻 |
| --- | --- |
| `PASS_CURRENT_STAGE` | 완료 정의와 게이트를 충족했고, 그 근거가 증거로 확인된다. 고도화 후보가 남아도 현재 단계는 통과 |
| `NEEDS_REVISION` | 완료 정의 미충족 또는 통과 근거 부족. 아키텍처를 고친 뒤 다시 돌려야 한다 |
| `CANNOT_VERIFY` | 아키텍처·증거·기록이 없어 통과 여부를 확인할 수 없다 |

**프로덕션 배포 가능 여부가 아니라 현재 교육 단계의 통과 여부**를 판정한다.
`/loop-run`의 `SUCCESS`를 그대로 옮겨 적지 않는다. **`SUCCESS`라도 근거가 없으면 `NEEDS_REVISION`이다.**

## 4. 문제 하나를 쓰는 형식 (파일 안)

모든 세션이 같은 모양이어야 한다. 상세 예시와 실패 사례 목록은 `references/upgrade-template.md`.

```markdown
### 문제 N. <교육생이 겪을 현상으로 제목을 쓴다>

| 항목 | 내용 |
| --- | --- |
| 확인 수준 | 실행으로 확인 / 증거로 확인 / 기록으로 확인 / 발생 가능성 있음 / 확인 불가 |
| 중요도 | 높음 / 보통 / 낮음 |
| 근거 파일 | `evidence/S01/run-02/manifest.json` (G3의 observed가 비어 있음) |
| 8문항 | 4 재루프 조건 |
| 9블록 | D 증거 규약 |

**무슨 일이 있었나**
(사실만. 관측값을 숫자로.)

**왜 그렇게 됐나**
(직접 원인 한두 문장.)

**루프 설계의 어느 빈틈 때문인가**
(어떤 조건이 없어서 미리 못 잡았는지.)

**해결책**
(교육생이 그대로 옮겨 적을 수 있는 구체 문장.)

**해결됐다고 볼 기준**
(다음 세션에서 무엇을 측정하면 되는지.)
```

## 5. 설명 방식 (15살 기준)

```text
결론부터 · 짧은 문장 · 한 문단에 한 문제
전문 용어는 처음 쓸 때 쉬운 뜻을 붙인다
문제를 화면과 행동으로 설명한다. 코드 위치만 말하지 않는다
비난하지 않고, 어린아이 취급도 하지 않는다
지금 올릴 수 있는 한 단계만 제시한다
```

설명 흐름은 항상 이 순서다.

```text
지금 무엇이 됐는가 -> 어떤 상황에서 문제가 되는가 -> 교육생은 무엇을 보게 되는가
-> 왜 그런가 -> 루프 설계에서 무엇이 빠졌는가 -> 다음 세션에 무엇을 넣어야 하는가
```

**좋은 예**

```text
G3은 PASS로 기록돼 있습니다.
그런데 manifest.json의 observed가 비어 있고, 증거 폴더에 해당 파일이 없습니다.
즉 "확인했다"는 말만 있고 확인한 흔적이 없습니다.
아키텍처에 "증거 파일이 없으면 PASS로 쓸 수 없다"는 규칙이 없어서 이렇게 통과했습니다.
다음 세션에서는 그 규칙을 블록 D에 넣으면 됩니다.
```

**나쁜 예**

```text
증거 수집 파이프라인의 무결성이 확보되지 않아 검증 신뢰도가 저하되었으므로
아티팩트 관리 체계를 리팩터링해야 합니다.
```

## 6. 적용 / 비적용

**적용한다**

- 한 세션의 루프가 끝난 뒤(`SUCCESS`/`EXHAUSTED`/`BLOCKED`/`ESCALATE`) 결과를 검토할 때
- `SUCCESS`가 선언됐는데 근거가 충분한지 의심될 때
- 다음 세션에서 아키텍처의 무엇을 올릴지 정할 때

**적용하지 않는다**

- 루프와 무관한 일반 코드 리뷰 → 평범한 리뷰로 처리한다
- 프로덕션 보안 감사, 대규모 성능·부하 테스트
- 코드 자동 수정, 루프 재실행 → `/loop-run`
- 아키텍처 설계·고도화 반영 → `/loop-builder`

## 7. 사용자에게 돌려줄 것

1. **파일 작성**: `upgrade/<세션>.md` (`references/upgrade-template.md` 양식 그대로)
2. **터미널 출력**: 아래 요약 카드만. 보고서 전문을 터미널에 다시 쏟지 않는다.

```markdown
## 루프 검토 완료 — 세션 S01

- **판정**: PASS_CURRENT_STAGE | NEEDS_REVISION | CANNOT_VERIFY
- **평가 수준**: 문서 기반 | 증거 기반 | 실행 기반
- **검토한 회차**: n회 / 증거 파일 k개
- **보고서**: `upgrade/S01.md`

### 한 줄 결론
<판정 이유 한 문장>

### 발견한 문제 (n개)
| # | 문제 | 확인 수준 | 9블록 | 8문항 |
| --- | --- | --- | --- | --- |

### 다음 할 일
`upgrade/S01.md`를 읽어 보신 뒤, **`/loop-builder`에 "고도화 반영해줘"**라고 말씀하시면
아키텍처가 S02로 올라갑니다. 반영하고 싶지 않은 항목이 있으면 그때 말씀해 주세요.
```

여기까지 쓰고 **멈춘다.** 교육생이 읽고 납득한 뒤 직접 판단하는 과정이 이 스킬의 핵심이다.

## 8. 보고 전 자기 점검

```text
[ ] upgrade/<세션>.md 를 references/upgrade-template.md 양식 그대로 썼는가
[ ] 문제가 3개를 넘지 않는가
[ ] 각 문제에 확인 수준 · 근거 파일 경로 · 해결책 · 확인 기준이 모두 있는가
[ ] 확인하지 않은 것을 확인했다고 쓰지 않았는가
[ ] 현재 실패와 다음 고도화를 섞지 않았는가
[ ] 8문항과 9블록 양쪽으로 지목했는가
[ ] 아키텍처 변경 지시서가 그대로 실행 가능한 문장인가
[ ] 평가 대상 파일을 하나도 고치지 않았는가 (쓴 파일은 upgrade/<세션>.md 하나뿐인가)
[ ] 판정이 셋 중 하나로 명시돼 있는가
[ ] 점수·백분율을 쓰지 않았는가
```
