대상 SPEC: $ARGUMENTS

`CLAUDE.md`의 제약, 경계, 정지 조건, 근거 규칙을 모두 따른다.

## 1. 준비
- `CLAUDE.md`, `MEMORY.md`, 대상 SPEC을 읽는다. `.draft.md`는 실행하지 않는다.
- `depends_on`의 SPEC이 `MEMORY.md`에서 "완료"가 아니면 중단하고 보고한다.
- `MEMORY.md`의 "반복된 실패"를 확인하고 같은 실수를 피한다.
- 이번이 몇 번째 회차인지 `MEMORY.md`로 확인한다. `max_iterations`를 넘기면 시작하지 않는다.

## 2. 선언
구현 전에 다음을 3~6줄로 먼저 적는다: 이번 회차에 만들 것, 범위 밖이라 만들지 않을 것, 이전 실패에서 반영할 것.

## 3. 구현
- SPEC에 적힌 것만 `tetris-loop-workshop/`에 만든다.
- SPEC에 없는 결정이 필요하면 추측하지 말고 `[사람 확인 필요]`로 보고하고 멈춘다.

## 4. 검증
다음 순서로 하고, 실제로 실행한 것만 결과로 쓴다.
1. 정적 점검 `[에이전트 확인]`: 파일 목록, 스크립트 불러오는 순서와 `defer`, 금지 패턴(외부 URL, `import`, `package.json`, `node_modules` 등) 검색.
2. 로직 점검 `[자동]`: Node가 있으면 `game.js`를 로드해 `test.js`의 검증을 가능한 범위에서 실행한다. 브라우저 없이 실행할 수 없으면 실행하지 못했다고 쓴다. Node 실행을 위해 프로젝트 폴더에 파일을 추가하지 않는다(필요하면 스크래치 위치를 쓴다).
3. 브라우저 화면, 콘솔 오류, 반응형(390px), 시각 확인 `[사람 확인 필요]`: SPEC의 수동 검증 절차를 그대로 사람에게 요청한다.

## 5. 실패 처리
- 실패하면 원인을 한 줄로 적고 고쳐서 다시 검증한다. 회차를 센다.
- 같은 실패 2회, 또는 `max_iterations` 도달이면 중단하고 보고한다.

## 6. 보고 (형식 고정)
- **결과 상태**: `완료` / `사람 확인 대기` / `중단` 중 하나.
- **완료 조건 표**: 조건 | 판정 | 근거 종류 | 근거(실행한 명령이나 확인한 파일). 근거가 없으면 `미확인`으로 쓴다.
- **사람 확인 요청**: 해야 할 절차와 기대 결과.
- **이번 회차**: n/max, 변경한 파일 목록.
- **다음 행동**: 사람이 해야 할 일 한 줄.
"완료"는 사람 확인 항목이 없고 모든 조건에 근거가 있을 때만 쓴다.

## 7. MEMORY.md 갱신
보고 직후 `MEMORY.md`를 갱신한다: 현재 상태, 마지막 실행, 반복된 실패(같은 유형이 2회 이상이면 승격), 열린 `[사람 확인 필요]`. 사람이 프롬프트로 전달한 결과가 있으면 `출처: 사람`으로 기록한다.
